# Отчёт по дефектам — «Мои файлы» (ru.company.filemanager) 1.0.0

**Объект:** Android-приложение «Мои файлы», пакет `ru.company.filemanager`, versionName `1.0.0`, versionCode `1` (к релизу не допущено).
**Артефакт:** `apk/base.apk`, sha256 `56722cf097ed3e3f118878dedcdaffca7edbe2e5cd8d0a6029b4458290f8478e`, подпись v2-only, cert `CN=cab-sa-dvo12496, O=Sberbank of Russia`, SHA-256 `94a8c7f1…a529`.
**Стенд динамики:** эмулятор `test_root_34` — Android 14 / API 34, AOSP `default`, arm64-v8a, root (`uid=0`, `u:r:su:s0`), Frida 16.7.19.
**Дата:** 2026-11-11. **Декомпиляция:** jadx + apktool; ключевое верифицировано по smali; часть выводов подтверждена рантайм-PoC (отмечено).

Термин «резилиенс» в отчёте не используется — вместо него «проверки окружения и защита от вмешательства (anti-tamper)».

# Часть 1. Перечень дефектов и нарушенные требования

Статусы: **PoC** — подтверждено рантайм-тестом на стенде; **статика** — по коду.
Группы: **A** — достижимые/эксплуатируемые; **B** — обходы проверок окружения (отдельный список); **C** — гигиена/низкий импакт.

## A. Достижимые / эксплуатируемые

### Д-1. Выход за пределы трёх разрешённых папок через «Выбрать папку» (`listCustomFolder`) — PoC
Метод `FileRepository.listCustomFolder` листит произвольный путь **без проверки вхождения** (`PathGuard.assertWithin`). Меню «Выбрать папку» предлагает тома вне песочницы (`/storage/emulated`, `/storage/self`, корни SD-карт). Раскрытие листингов каталогов (имена файлов) за пределами Download / DCIM-Camera / Documents.

Нарушает требования:
- **req 33:** «Запрещён доступ к каталогам и файлам, находящимся вне доверенной области, если это не разрешено политикой MDM.»
- **req 34:** «Единственная функция приложения — удаление содержимого заданных папок по кнопке. Нет просмотра, открытия, создания, изменения и передачи файлов.» (новая редакция: просмотр списка, открытие во viewer и удаление **в трёх разрешённых папках**).
- **req 42:** «Пути строятся через Environment.getExternalStoragePublicDirectory() (DIRECTORY_PICTURES, DIRECTORY_DCIM, DIRECTORY_DOWNLOADS) и канонизируются. Только основной том; SD-карта и USB-OTG не затрагиваются.»
- **req 43:** «Перед удалением каждого объекта канонический путь проверяется на вхождение в одну из трёх папок (startsWith(root + "/")). Обход без следования по symlink (Files.walkFileTree без FOLLOW_LINKS) и без пересечения точек монтирования.» (нарушена часть «проверка вхождения перед доступом» для операции листинга).

### Д-2. В киоск-режиме приложение открывает системный экран Настроек — PoC
При отсутствии доступа к файлам показывается баннер, по клику открывается системный экран All-Files-Access. Нет сообщения «обратитесь к администратору». Точка выхода из Lock Task в Настройки; пользователь сам выдаёт доступ ко всему хранилищу.

Нарушает требования:
- **req 41:** «Грант выдаётся только политикой MDM пользователю. В киоске экран Настроек не открывается; при isExternalStorageManager() == false — ошибка "обратитесь к администратору" (не поднимать окно-запрос на выдачу доступа внутри приложения).»

### Д-3. Передача файла во внешний viewer без проверки его подлинности — статика
Открытие файла идёт явным `setPackage("ru.sber.irmviewer.cerber")`, но подпись получателя не проверяется (нет `<queries>` и `hasSigningCertificate`). Приложение-двойник с тем же именем пакета и чужой подписью получит файл и URI-грант на чтение.

Нарушает требования:
- **req 22:** «Передача файлов — только явными (explicit) интентами из доверенного списка целевых приложений; broadcast-рассылки с содержимым запрещены.» (в части проверки подлинности получателя).
- **req 20:** «Файлы не предоставляются другим приложениям через ContentProvider; доступ только внутри приложения.» (передача во viewer допущена новой редакцией — но без аутентификации получателя).
- **23.1.35:** «Ограничение доступа к ресурсам. Не предоставлять доступ к программным ресурсам приложения другим приложениям.»

## B. Обходы проверок окружения и защиты от вмешательства (отдельный список)

> Все проверки среды в приложении (отладка, root, целостность, нативная анти-отладка) вычисляются **один раз** в `FileManagerApp.onCreate`, решение принимается в необфусцированных Java-методах, а реакция — `terminateApplication()` (убийство процесса). По нашей BB-модели root/Frida/adb на устройстве жертвы — вне скоупа, поэтому это не эксплуатируемый вектор, а дефекты реализации защиты от анализа; важны для внутреннего аудита и демонстрации разработке.

### Д-4. Контроль целостности бесполезен — подпись сравнивается сама с собой — PoC
`IntegrityChecker` берёт эталонный хэш подписи из **живого** сертификата в рантайме (не захардкожен), затем сверяет текущую подпись с ним же. Репак + ресайн любым ключом проходит проверку. Подтверждение: обновлённый билд подписан **другим** ключом и запускается.

Нарушает требования:
- **23.1.2:** «Защита от внесения изменений. Контроль целостности исполняемого модуля и ресурсов (Android SafetyNet Attestation / Play Integrity). При выявлении изменений — прекратить работу.»

### Д-5. Все проверки окружения снимаются одним хуком / структурно слабы — PoC
Единая точка оценки (`onCreate`), решение в Java (`isDeviceSafe`, `isDeviceRooted`, `isDebuggable`, `isIntegrityValid`, `NativeSecurityChecker.a()` — имена не обфусцированы), нативная библиотека лишь возвращает `int` в Java. Хук Java-границы → приложение работает на руте. Нет повторных/фоновых проверок и проверок перед чувствительными операциями.

Нарушает требования:
- **23.1.1:** «Защита от отладки. При выявлении отладочных процедур приложение должно прекратить работу.»
- **23.1.5:** «Работа на jailbreak/root-устройствах. Приложение не должно работать на устройствах с root/jailbreak. Контроль целостности платформы (SafetyNet/Play Integrity).»

### Д-6. Отсутствует детект инструментирования (Frida/hooking) — статика
Ни в `libsecurity.so`, ни в smali нет ни одной анти-Frida/анти-hook сигнатуры (нет сканов `frida`/`gum-js-loop`/портов 27042, `/proc/self/maps`, xposed, named pipes). Нативная библиотека — только анти-отладка (ptrace + TracerPid).

Нарушает требования:
- **23.1.2 / 23.1.5** (в части «контроль целостности платформы» — инструментирование не детектируется).

### Д-7. Детект root одноканальный и слабый — статика
`RootDetector.isDeviceRooted` = наличие 10 захардкоженных su-путей + `Build.TAGS` содержит `test-keys`/`dev-keys`/`unsigned-release`. Нет проверок `which su`/PATH, mount, SELinux, пакетов супер-пользователя, Magisk-артефактов. Обходится file-hiding / Magisk DenyList + спуфом `ro.build.tags`.

Нарушает требования:
- **23.1.5:** «Приложение не должно работать на устройствах с root/jailbreak…»

### Д-8. Репак в debuggable отключает все проверки окружения — статика
В `FileManagerApp.onCreate`: если `applicationInfo.flags & 2` (debuggable) — выполняется ранний `return` **до** `isDeviceSafe()`, то есть root/integrity/anti-debug не проверяются, плюс включается подробное логирование. Патч одной строки манифеста/smali.

Нарушает требования:
- **23.1.1, 23.1.5** (проверки выключаются тривиальной модификацией), **23.1.23** косвенно (release-режим обходится репаком).

### Д-9. Самозавершение при включённом режиме разработчика бьёт по легитимному пользователю — PoC
`DebugDetector.isDebuggable` считает `development_settings_enabled == 1` признаком отладки → `isDeviceSafe()` = false → `terminateApplication()` (`killProcess` + `exit`). На стенде — death-loop (10 самозавершений за 2 c). Рекомендованная практика — мягкая деградация, а не креш.

Нарушает требования:
- **23.1.7:** «Режим разработчика. Не запускаться на устройствах с включённым режимом разработчика.» (формально срабатывает, но реализация — само-DoS; предмет новой редакции).

## C. Гигиена / низкий импакт

### Д-10. Подпись только по схеме v2
Нет v3/v3.1 → нет пути ротации ключа. Нарушает: **(гигиена, прямого требования нет; смежно с 23.1.2)**.

### Д-11. Пустые правила бэкапа
`allowBackup="false"` есть, но `dataExtractionRules`/`fullBackupContent` пустые → канал device-transfer (D2D) на Android 12+ не исключён. Нарушает:
- **req 25:** «Резервное копирование отключено: android:allowBackup="false" + явные dataExtractionRules/fullBackupContent.»

### Д-12. Нет лимитов обхода при удалении
`walkFileTree` с `maxDepth = Integer.MAX_VALUE`, без лимита количества; foreground-сервиса в этом билде нет → длинная очистка оборвётся при закрытии. Нарушает:
- **req 39:** «Обход итеративный, вне main thread, с лимитами глубины и количества. Ошибка на отдельном файле не прерывает очистку. Итог на экране: удалено N, не удалено M.» (в части лимитов и устойчивости).

### Д-13. Имя файла попадает в системный журнал
При открытии во viewer системный лог `ActivityTaskManager: START` содержит `content://…/<имя файла>` (ПДн). Нарушает:
- **23.1.32:** «Чувствительная информация в журналах. Запрет записи банковской тайны, ПДн, ключей в журналы аудита/технологические журналы.» (частично; канал — системный лог, вне контроля приложения).

### Д-14. Частичная обфускация
Имена security-методов (`isDeviceRooted`, `isIntegrityValid` …) и строки проверок (`test-keys`, su-пути, сообщения) — в открытом виде. Нарушает:
- **23.1.3:** «Защита от инженерного анализа. Обфускация имён классов/методов, строковых констант, критичных участков кода.»

### Д-15. Разрешение `MANAGE_EXTERNAL_STORAGE` шире необходимого
Функции (три публичные папки, типы документов/изображений) покрываются scoped-storage / SAF без All-Files-Access. Принято по БТ, но это максимальный storage-scope. Нарушает (частично):
- **req 23:** «Приложение запрашивает только минимально необходимые разрешения… По возможности использоваться Storage Access Framework (SAF) / scoped storage вместо глобального разрешения.»

### Д-16. FLAG_SECURE не на окнах диалогов
`FLAG_SECURE` стоит на главном окне (подтверждено — скриншот чёрный), но на окнах диалогов (показывают имена файлов) не подтверждён. Нарушает (частично):
- **23.1.4:** «Отключение скриншота (FLAG_SECURE)…» / **23.1.38:** «Фоновый режим… размытие/безопасный экран…».

# Часть 2. Детальный разбор дефектов

## Д-1. Выход за пределы трёх папок через «Выбрать папку» → `listCustomFolder`

**Описание.** Приложение ограничивает работу тремя публичными папками (Download, DCIM/Camera, Documents) через `PathGuard.assertWithin` + `AllowedRoots`. В обновлённой сборке добавлены пункт меню «Выбрать папку» и метод `FileRepository.listCustomFolder`, который листит переданный путь **без проверки вхождения**. Список в пикере строится из трёх корней **плюс** перечисления `/storage` с инвертной фильтрацией, из-за чего в него попадают тома вне песочницы.

**Место в коде.**
- `fs/FileRepository.java:139` — `listCustomFolder(AllowedFolder folder, String customPath)` → `new File(customPath).listFiles()`; `PathGuard.assertWithin` **не вызывается** (ср. `listFolder` на :166, где `assertWithin` есть).
- `ui/FilesViewModel.java:140` — `openCustomFolder(String customPath)` → корутина `o3/s` → `repo.listCustomFolder(AllowedFolder.CUSTOM, path)` (`o3/s.java`, вызов listCustomFolder).
- `ui/MainActivity.java:368` — обработчик меню `action_choose_folder`; `:377–381` добавляет 3 корня; `:384` `new File("/storage").listFiles(new o3.j())` (фильтр `o3/j.java` = `isDirectory()` — принимает все); фильтр-отсев по корням — `MainActivity.smali` (метод `onCreate$lambda$0`, строки ~1566–1585: `l.a0`=startsWith, `if-eqz … :cond_7` → совпадение с корнем = **пропуск** добавления, иначе `:cond_8 :goto_4 add`). То есть добавляются записи, **не** начинающиеся ни с одного корня.
- `fs/AllowedFolder.java:16` — добавлен enum-член `CUSTOM`.

**Логи рантайм-тестирования** (`poc/poc_escape.js`, эмулятор, доступ MANAGE_EXTERNAL_STORAGE выдан):
```
[listCustomFolder] /storage/emulated/0 (16): ["Alarms","Android",…,"Documents_CONFIDENTIAL.pdf","ROOT_SECRET.txt","ui.xml"]
[listCustomFolder] /storage/emulated/0/Pictures (2): [".thumbnails","OUTSIDE_SECRET.txt"]      // Pictures не разрешена
[listCustomFolder] /storage/emulated/0/Download (1): ["inside_download.txt"]                     // контроль: внутри
[assertWithin] /storage/emulated/0/Pictures -> BLOCKED: SecurityException: Недопустимый путь вне разрешённых каталогов
```
Контраст доказан: тот же путь `listCustomFolder` показывает, а `PathGuard.assertWithin` отвергает.

**Влияние на безопасность.** Раскрытие содержимого каталогов (имена файлов, размеры, даты) за пределами доверенной области — включая корень общего хранилища и SD-карты. Это нарушение политики изоляции приложения (вектор — выход за песочницу). Удаление и передача во viewer за пределами трёх папок остаются закрыты (`delete` → `assertWithin` → SecurityException; `openInIrmViewer` → FileProvider двойная канонизация → IllegalArgumentException), поэтому прямого удаления/эксфильтрации нет — импакт ограничен раскрытием листингов. При наличии на устройстве чувствительных файлов в других каталогах (другие приложения, SD) их имена становятся видимы оператору.

**Шаги воспроизведения.**
1. Запустить приложение, выдать доступ к файлам.
2. Меню (⋮) → «Выбрать папку».
3. В списке выбрать том вне трёх папок: `/storage/emulated`, `/storage/self` или корень SD-карты.
4. Приложение покажет листинг выбранного каталога — вне Download/DCIM-Camera/Documents.
   (Эквивалент на уровне кода — `poc/poc_escape.js`: прямой вызов `listCustomFolder` на `/storage/emulated/0` и `/Pictures`.)

**Рекомендации по исправлению.**
- В `listCustomFolder` выполнять `PathGuard.assertWithin(file, AllowedRoots.allPaths())` **до** `listFiles()` — так же, как в `listFolder`; при выходе за корни возвращать пустой список/ошибку.
- Из пикера «Выбрать папку» убрать перечисление `/storage` и не-корневые тома; оставить только три разрешённых корня (и, при необходимости, их подпапки, проверяемые через `assertWithin`). Починить инвертный фильтр (сейчас он оставляет именно не-корневые пути).
- Канонизировать `customPath` и запретить пересечение точек монтирования (единый метод валидации для всех операций — list/delete/share). Эшелонированная защита: граница держится не выбором источника пути, а проверкой пути перед каждой файловой операцией (secure-coding: file-upload-handling — канонизация и allow-list базового каталога).

## Д-2. Киоск открывает системный экран Настроек

**Описание.** При `Environment.isExternalStorageManager() == false` показывается баннер; его нажатие запускает системный экран выдачи All-Files-Access. По БТ для киоска переход в Настройки запрещён, а должно отображаться сообщение «обратитесь к администратору».

**Место в коде.**
- `ui/MainActivity.java:862` — `Environment.isExternalStorageManager()` управляет видимостью `permissionBanner`.
- `ui/MainActivity.java:466` → `openAllFilesAccessSettings()`; `:515–529` — `startActivity(Intent("android.settings.MANAGE_APP_ALL_FILES_ACCESS_PERMISSION"))` с фолбэком `MANAGE_ALL_FILES_ACCESS_PERMISSION`.
- Сообщения/ветки «обратитесь к администратору» в коде нет.

**Логи рантайм-тестирования.** При первом запуске приложение показало баннер «нужен доступ к файлам»; клик открывает системный экран All-Files-Access (подтверждено инженером на экране стенда). Для продолжения PoC доступ выдан командой `adb shell appops set ru.company.filemanager MANAGE_EXTERNAL_STORAGE allow` (без перехода в Настройки).

**Влияние на безопасность.** В Lock Task Mode это потенциальный выход в системные Настройки (обход изоляции киоска). Кроме того, модель предполагает выдачу MANAGE_EXTERNAL_STORAGE только Монитором при подготовке устройства — внутриприложенческий запрос эту схему нарушает.

**Шаги воспроизведения.**
1. Отозвать доступ: `adb shell appops set ru.company.filemanager MANAGE_EXTERNAL_STORAGE default`.
2. Запустить приложение → появляется баннер.
3. Нажать баннер → открывается системный экран управления доступом ко всем файлам.

**Рекомендации по исправлению.**
- Убрать запуск `android.settings.*` из приложения. При `isExternalStorageManager() == false` показывать неинтерактивное сообщение «обратитесь к администратору».
- Доступ выдаёт только MDM (Монитор) при провижининге. Наименьшие привилегии: не инициировать выдачу разрешений из UI (secure-coding: mobile-app-security — least privilege, security-решения вне клиента).

## Д-3. Передача файла во viewer без проверки подписи получателя

**Описание.** Открытие документа идёт явным интентом в пакет `ru.sber.irmviewer.cerber` с READ-грантом, но подлинность получателя (подпись) не проверяется, а пакет не объявлен в `<queries>`.

**Место в коде.**
- `ui/MainActivity.java:89` — `IRM_PACKAGE = "ru.sber.irmviewer.cerber"`.
- `ui/MainActivity.java:~553–559` — `getUriForFile(…)` → `VIEW` + `setDataAndType` + `addFlags(1)` (READ) + `setPackage(IRM_PACKAGE)`.
- `AndroidManifest.xml` — секции `<queries>` нет; `hasSigningCertificate`/`GET_SIGNING_CERTIFICATES` в коде нет.

**Логи рантайм-тестирования.** Не выполнялось (требует установки подменного viewer с тем же пакетом) — статика; предлагается как стендовый сценарий.

**Влияние на безопасность.** Приложение-двойник, объявившее пакет `ru.sber.irmviewer.cerber` с чужой подписью и установленное вместо/раньше настоящего, получит открываемый файл и URI-грант на чтение. Импакт ограничен одним пользовательски выбранным файлом (read-only), но нарушает требование аутентификации получателя. На Android 11+ без `<queries>` приложение к тому же «не видит» целевой пакет для корректной проверки.

**Шаги воспроизведения (стенд).**
1. Собрать приложение-заглушку с `package="ru.sber.irmviewer.cerber"`, `intent-filter` на `VIEW`, подписанное другим ключом.
2. Удалить/не устанавливать настоящий viewer, установить заглушку.
3. В «Мои файлы» открыть документ → заглушка получает `content://`-URI и читает файл.
4. Проверка гранта: `adb shell dumpsys activity permissions` — должен быть только READ на один URI.

**Рекомендации по исправлению.**
- Объявить `<queries><package android:name="ru.sber.irmviewer.cerber"/></queries>`.
- Перед передачей проверять подпись получателя: `packageManager.hasSigningCertificate(IRM_PACKAGE, <SHA-256 ожидаемого серта>, CERT_INPUT_SHA256)`; при несовпадении/отсутствии — ошибка без выбора другого приложения.
- Грант — только READ, без `FLAG_GRANT_PERSISTABLE`/`FLAG_GRANT_PREFIX`; по возможности отзывать после возврата. (secure-coding: certificate-hygiene — проверять конкретный сертификат, а не только имя.)

## Д-4. Контроль целостности сравнивает подпись сам с собой

**Описание.** `IntegrityChecker.init` сохраняет эталонный хэш подписи, вычисленный из **текущего** сертификата в рантайме; `isIntegrityValid` сверяет текущую подпись с этим же (саморассчитанным) значением. Захардкоженного эталона нет. Любой репак с переподписью проходит проверку.

**Место в коде.**
- `security/IntegrityChecker.java` — `init()` (`f3249b = computeSignatureHash(ctx)`), `isIntegrityValid()` (`:77`) сравнивает `computeSignatureHash(ctx)` с `f3249b`; `computeSignatureHash` берёт `getPackageInfo(pkg, GET_SIGNING_CERTIFICATES)`. Эталон-константы в коде/ресурсах нет (проверено грепом 64-hex: только `.source "r8-map-id-…"`).
- `smali/.../IntegrityChecker.smali` — `sput … f3249b` из `computeSignatureHash`, захардкоженного хэша нет.

**Логи рантайм-тестирования.** Обновлённый билд подписан **другим** ключом (cert SHA-256 `94a8c7f1…` против `79d59a51…` в прошлой сборке) и штатно запускается (под обходом root) — то есть смена подписи контролем не детектируется.

**Влияние на безопасность.** Защита от модификации и переупаковки фактически отсутствует: злоумышленник переупаковывает APK (внедряет код/меняет ресурсы), переподписывает своим ключом — проверка целостности проходит. Единственный реальный барьер против репака — проверка v2-подписи самой ОС при установке, которую этот код не дублирует.

**Шаги воспроизведения.**
1. `apktool d base.apk` → изменить код/ресурсы → `apktool b` → подписать **своим** ключом (`apksigner sign`).
2. Установить → приложение запускается (при снятых проверках root на стенде), `isIntegrityValid` возвращает true.

**Рекомендации по исправлению.**
- Либо захардкодить (и обфусцировать/вынести в нативку) ожидаемый SHA-256 сертификата **разработчика** и сверять с ним (а не с живым), либо — предпочтительно — перенести проверку целостности на серверную аттестацию (Play Integrity с проверкой вердикта на бэке). При офлайн-работе — локальная проверка против захардкоженного эталона в нативном коде с анти-Frida.
- Реакция на несовпадение — мягкая деградация/ограничение, не обязательно креш (secure-coding: mobile-app-security — «деградируйте мягко, не крешитесь»; «проверяйте подпись приложения в рантайме» против фиксированного эталона).

## Д-5. Проверки окружения снимаются одним хуком

**Описание.** Проверки среды выполняются один раз при старте и решаются в необфусцированных Java-методах; нативная библиотека только возвращает `int`. Хук Java-границы отключает все проверки сразу.

**Место в коде.**
- `FileManagerApp.java:16` — `isDeviceSafe()` = `!isDebuggable && !isDeviceRooted && isIntegrityValid`; `:44–47` — `isDeviceSafe()` ? `IntegrityChecker.init` : `terminateApplication()`.
- `security/NativeSecurityChecker.java` — `a()` = `combinedCheck()` (нативный) с fail-closed; результат читает Java.
- Имена методов не переименованы R8 (`isDeviceSafe`, `isDeviceRooted`, `isDebuggable`, `isIntegrityValid`).

**Логи рантайм-тестирования** (`poc/bypass.js`, Frida spawn):
```
[bypass] DebugDetector.isDebuggable -> false
[bypass] RootDetector.isDeviceRooted -> false
[bypass] IntegrityChecker.isIntegrityValid -> true
→ приложение не самозавершается, MainActivity в foreground (topResumedActivity)
```
Без обхода — death-loop: `ActivityManager: Process ru.company.filemanager (pid …) has died: fg TOP`, 10 самозавершений за 2 c; `pidof` прыгает (`-,9119,-,-,-,9159`).

**Влияние на безопасность.** Защита от анализа не выдерживает стандартного инструментирования: один Frida-скрипт нейтрализует root/debug/integrity/anti-debug. По BB-модели (root/Frida на устройстве жертвы — вне скоупа) это не эксплуатируемый вектор, но для внутренней модели угроз — отсутствие реальной защиты.

**Шаги воспроизведения.** `frida -U -f ru.company.filemanager -l poc/bypass.js` (spawn) → приложение запускается на руте.

**Рекомендации по исправлению.**
- Перенести критичное решение и реакцию (`abort`) в нативный код с обфускацией строк/потока управления и анти-Frida; не оставлять единую Java-точку `isDeviceSafe`.
- Выполнять проверки не единожды при старте, а периодически и перед чувствительными операциями.
- Основной барьер против модификации — серверная аттестация устройства/приложения (где применимо), т.к. любой локальный контроль обходится (secure-coding: mobile-app-security — «устройство враждебно», эшелонированная защита, security-решения на сервере).

## Д-6. Нет детекта инструментирования (Frida/hooking)

**Описание.** В приложении отсутствует детект code-injection/hooking. Нативная библиотека делает только анти-отладку.

**Место в коде.**
- `lib/*/libsecurity.so` — экспортирует `ptraceCheck`, `procStatusCheck`, `combinedCheck`; PLT-импорты: `ptrace`, `fopen`/`fread` (`/proc/self/status`), `__system_property_get`. Строки — только `TracerPid`/`ptrace`.
- Грепы по `smali/` и строкам `.so`: `frida|gum|xposed|substrate|27042|/proc/self/maps` — 0 попаданий.

**Логи рантайм-тестирования.** Frida-инструментирование выполнено без срабатывания какого-либо анти-Frida (см. Д-5).

**Влияние на безопасность.** Hooking-инструменты (Frida/Substrate) приложением не обнаруживаются, что и позволяет обход Д-5.

**Рекомендации по исправлению.** Добавить индикаторы инструментирования (сканы `/proc/self/maps` на gum/frida-библиотеки, именованные потоки `gmain`/`gum-js-loop`, прослушиваемые порты, D-Bus), выполняемые из обфусцированного нативного кода; реакция — мягкая деградация. Принять игру «кошки-мышки» и повышать стоимость обхода (secure-coding: mobile-app-security — «детекция code-injection / method-hooking»).

## Д-7. Детект root одноканальный и слабый

**Описание.** Единственные признаки root — существование su-файлов и теги сборки. Легко скрыть.

**Место в коде.** `security/RootDetector.java:58` — `isDeviceRooted` = `checkSusPaths()` (10 путей) `|| Build.TAGS содержит test-keys || checkMagiskBuildProps()` + нативный анти-дебаг. Список `SU_PATHS` захардкожен и виден в открытую.

**Логи рантайм-тестирования.** На стенде `Build.TAGS=test-keys` → `isDeviceRooted` = true → самозавершение (см. Д-5). Обход — хук или скрытие признаков.

**Влияние на безопасность.** На реальном root (Magisk) достаточно DenyList/скрытия su и спуфа `ro.build.tags`, чтобы детект не сработал.

**Рекомендации по исправлению.** Многоканальный детект (which/PATH, mount-опции `/system`, SELinux-режим, наличие Magisk-артефактов/пакетов, проверка `ro.debuggable`, попытка записи в `/system`), из нативного обфусцированного кода; строки-признаки не хранить в открытом виде. Реакция — мягкая деградация.

## Д-8. Репак в debuggable отключает все проверки

**Описание.** Ветка debuggable делает ранний выход из `onCreate` до проверок.

**Место в коде.** `FileManagerApp.java:onCreate` — вычисляется `zBooleanValue = (flags & 2) != 0`; `SecureLogger.setDebugEnabled(zBooleanValue)`; `if (zBooleanValue) return;` — до `isDeviceSafe()`/`IntegrityChecker.init`.

**Логи рантайм-тестирования.** Не выполнялось (статика); демонстрируется репаком с `android:debuggable="true"`.

**Влияние на безопасность.** Переупаковка в debuggable-сборку отключает root/integrity/anti-debug и включает подробное логирование — усиливает Д-4 (переупакованная сборка и не проверяется, и логирует).

**Рекомендации по исправлению.** Не завязывать отключение проверок на debuggable-флаг; наоборот, debuggable в release трактовать как признак компрометации. Логирование гейтить отдельно от проверок окружения.

## Д-9. Самозавершение при режиме разработчика (само-DoS)

**Описание.** Включённый режим разработчика трактуется как небезопасность и приводит к `terminateApplication()` на релизной сборке, затрагивая легитимного пользователя.

**Место в коде.** `security/DebugDetector.java` — `isDeveloperModeEnabled` (`development_settings_enabled==1`) входит в `isDebuggable`; `FileManagerApp.java` — при `!isDeviceSafe()` → `terminateApplication()` (`Process.killProcess` + `System.exit(1)`).

**Логи рантайм-тестирования.** На стенде приложение самозавершается в цикле (10 раз/2 c) — проявление той же `terminateApplication`.

**Влияние на безопасность.** Не защитный эффект, а анти-юзабилити/само-DoS: легитимный пользователь с включённой отладкой не может пользоваться приложением; устройство при этом не скомпрометировано.

**Рекомендации по исправлению.** Режим разработчика не приравнивать к небезопасности и не крешить приложение; при необходимости — предупреждение/ограничение функций. Общая практика для детектов среды — мягкая деградация (secure-coding: mobile-app-security).
