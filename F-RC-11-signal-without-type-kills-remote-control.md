# F-RC-11 — Один некорректный сигнал устройства отключает удалённое управление для всех администраторов до перезапуска сервера

**Severity: по тяжести воздействия — High; по классу — отказ в обслуживании.**
Вендор завёл по этому дефекту задачу **SM-15276** с приоритетом «Высокий»
(компонент ARM-3, исправление запланировано в 17.0.3).

| | |
|---|---|
| Компонент | `arm` (`emm/arm:altair-17.0.1-jammy-48fc3ee-j25`) |
| Обнаружено | 20.10.2026 в ходе тестирования (воспроизведено непреднамеренно) |
| Подтверждено вендором | 21.10.2026, задача SM-15276 |
| Статус | открыта |

---

## Суть

Сигнал от устройства **без поля `type`** вызывает необработанное исключение в
плановой задаче опроса сигналов `WebRTCSchedulingService.pollSignal`. После
одного такого исключения задача больше не выполняется: сервер перестаёт
передавать в браузеры сигналы **всех устройств для всех администраторов**.

Удалённое управление не работает до перезапуска `arm`.

Хранимая процедура `sp_remote_srv_add_signal` записывает сигнал в
`remote_signal` без проверки структуры, а `WebRTCServiceImpl.isFindSignal`
(строка 405) вызывает `asString()` у поля `type` без проверки наличия и типа.

---

## Воспроизведение

1. Открыть в консоли удалённое управление устройством — создаётся комната,
   сессия браузера попадает в набор опроса.
2. От имени устройства отправить в эту комнату сигнал без поля `type`:

   ```json
   {"sdp": "v=0", "room": <id комнаты>}
   ```

3. В течение интервала опроса (3 с) задача падает с исключением.
4. Открыть удалённое управление **любым другим** устройством — сигналы
   устройства до браузера больше не доходят.

Нашим инструментарием это теперь **намеренно затруднено**: отправка сигнала без
`type` требует явного разрешения, иначе SDK отказывает со ссылкой на эту
находку.

---

## Доказательство

Сигнал в базе, записанный за секунду до ошибки:

```
remote_signal: id=2001, room_id=441, s_sender=SS, create_date=2026-10-20 14:23:43,
s_data={"sdp": "v=0", "room": 441}
```

Исключение в `arm`:

```
ERROR [MessageBroker-3] o.s.s.s.TaskUtils$LoggingErrorHandler
  Unexpected error occurred in scheduled task
tools.jackson.databind.exc.JsonNodeException: 'ObjectNode' method `asString()`
  cannot coerce value {...(0 properties)} to `java.lang.String`
  at com.safephone.service.WebRTCServiceImpl.isFindSignal(WebRTCServiceImpl.java:405)
  at com.safephone.service.WebRTCServiceImpl.pollSignals(WebRTCServiceImpl.java:236)
  at com.safephone.service.WebRTCSchedulingService.pollSignal(WebRTCSchedulingService.java:41)
```

Наблюдаемая картина со стороны участников сеанса:

* устройство получает `WebRTCStart`, отвечает `Answer` и `IceCandidate`, сигналы
  записываются в `remote_signal`;
* браузер их не получает: за сеанс по `/messages` ему передаётся 88 байт
  служебных кадров против ~1,4 КБ в рабочем сеансе;
* браузер не применяет ответ устройства и не создаёт разрешение TURN на его
  relay-адрес; устройство отключается по `connectTimeoutSeconds` с
  `Disconnect: Timed out waiting for 30000 ms`;
* в журнале `arm` исключение записано один раз, повторных запусков задачи нет.

После перезапуска `arm` 21.10.2026 12:53 UTC удалённое управление
восстановилось: сеанс в 12:57 передал через TURN около 520 КБ.

## Влияние

**Одно сообщение от одного устройства отключает удалённое управление во всей
установке.** Источник — управляемое устройство, то есть наименее доверенная
сторона в модели MDM. Привилегии не нужны: достаточно быть зарегистрированным
устройством.

Восстановление требует ручного вмешательства администратора инфраструктуры
(`docker-compose restart arm3`) — само по себе состояние не проходит.

Отдельно стоит отметить **скрытность отказа**: консоль продолжает показывать
устройства подключёнными, ручка конфигурации сеанса отвечает `ok`, журнал
аудита исправно пишет «Открытие сессии удаленного управления». Администратор
видит только то, что подключение не устанавливается, и естественным образом
подозревает сеть или устройство, а не сервер.

По правилам программы отказ в обслуживании оценивается невысоко; окончательная
оценка за заказчиком. Отмечу лишь, что вендор самостоятельно присвоил задаче
приоритет «Высокий».

## Сопутствующие дефекты разбора (из той же задачи)

Необработанные исключения в обработчике `offer` на некорректных данных —
уровень ERROR, на опрос сигналов не влияют:

* `NullPointerException` в `WebRTCController.offer` (строка 78) — `Set.copyOf`
  над списком `privilege` с элементом `null`, зафиксировано 39 раз;
* `Cannot deserialize value of type ArrayList<PrivilegeWebRtcEnum> from String
  value` — `privilege`, переданный строкой: комната не создаётся, а последующие
  сигналы падают с «Комната удалённого управления не найдена»
  (`sp_remote_adm_signal_write`, RC=-31200);
* ошибки разбора в `WebRTCController.getOfferDTO` и
  `SmUtilsService.fromJsonWithException` на нечисловых и выходящих за диапазон
  `int` значениях.

Это согласуется с нашим наблюдением
([Low/Info, N-4](low-and-info-notes.md)): сервер не проверяет типы полей
оффера, а на отброшенную команду отвечает оператору `ok`.

---

## Рекомендации

1. Проверять наличие и тип поля `type` до разбора (`isFindSignal`), некорректный
   сигнал отбрасывать с записью в журнал.
2. Обернуть тело плановой задачи в обработчик исключений, чтобы единичная ошибка
   не останавливала опрос; убедиться, что флаг занятости сбрасывается в
   `finally`.
3. Валидировать структуру сигнала на уровне `sp_remote_srv_add_signal`.
4. Добавить наблюдаемость: если плановая задача перестала выполняться, это
   должно быть видно в метриках и журнале, а не только по жалобам
   администраторов.

---

## Важное замечание о ходе работ

Этот дефект был воспроизведён **непреднамеренно**, в ходе проверки устойчивости
сервера к некорректным данным от устройства. Он на двое суток вывел из строя
удалённое управление на стенде и исказил часть наших собственных измерений: в
частности, сквозная проверка [F-RC-5](F-RC-5-html-injection-operator-console.md)
не сходилась именно по этой причине, и мы ошибочно считали это неисправностью
стенда. После перезапуска `arm` фича работает штатно.

Приносим извинения за простой стенда. В инструментарий добавлена защита:
отправка сигнала без поля `type` теперь требует явного подтверждения.
