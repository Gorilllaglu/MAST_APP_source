# UrlTest — приложение ru.sting.UrlTest

Учебное iOS-приложение (Swift, UIKit, min iOS 15.6) с намеренно
заложенными дефектами. Артефакт — `UrlTest-1.0-adhoc.ipa`, исходники
рядом в `UrlTest/`. Слабости распределены по четырём областям:
конфигурация сети, хранение данных, обработка URL-схем и метаданные
`Info.plist`.

## Что заложено в приложение

### 1. Конфигурация сети и передача чувствительных данных

В `Info.plist` на верхнем уровне указано `NSAppTransportSecurity` с
`NSAllowsArbitraryLoads = true` — App Transport Security выключен
глобально, приложению разрешён HTTP без TLS на любые домены. Это
подтверждается и в собранном IPA (`Payload/UrlTest.app/Info.plist`),
то есть настройка доехала до артефакта, а не осталась в конфиге
разработчика.

Поверх этого экран «Network Requests» содержит шесть жёстко зашитых
запросов, каждый из которых кладёт секрет в свою часть HTTP-запроса:

1. **Пароль в заголовке**: `X-Auth-Token: password=qwerty123` на
   `https://yandex.ru/`.
2. **Push-токен в заголовке**: тот же `X-Auth-Token` несёт полный
   push-токен FCM-формата длиной 152 символа
   (`AAAAODDc_Do:APA91bG5...`).
3. **Пароль в query-параметре**: `http://ya.ru/?password=123qwerty` —
   секрет в URL, причём по **cleartext HTTP**.
4. **Пароль в пути URL**: `https://yandex.ru/password=qwerty123/`.
   Даже под TLS такой URL утекает в логи прокси, реферер и историю.
5. **API-ключ поверх HTTP**: `Authorization: Bearer
   secret_api_key_12345` на `http://httpbin.org/get`.
6. **Учётные данные в теле поверх HTTP**:
   `{"username": "admin", "password": "P@ssw0rd!"}` на
   `http://httpbin.org/post`.

Запросы уходят через `URLSession.shared` без `URLSessionDelegate` —
проверка сертификата не переопределена ни в одном месте приложения,
certificate pinning отсутствует полностью. Плюс `buildURLRequest()`
строит запрос с `cachePolicy: .useProtocolCachePolicy`, поэтому URL
с паролем в query и в пути оседает в дисковом кэше `Cache.db`.

Расположение: `Info.plist:5-9`,
`UrlTest/NetworkRequestsViewController.swift:53-130` (список запросов
и сборка `URLRequest`), `:323` (отправка).

### 2. Хранение данных

При первом запуске `AppDelegate` делает две вещи, обе небезопасные.

1. **Токен доступа в UserDefaults**: захардкоженная строка
   `qweasdzxc123qweasd` пишется в `UserDefaults.standard` под ключ
   `access_token`. UserDefaults — это незашифрованный plist в
   контейнере приложения; Keychain в приложении не используется
   вообще (ни одного вызова `SecItem*`, `kSec*`, `CryptoKit` во всём
   проекте).
2. **Файл с учётными данными открытым текстом**: создаётся
   `Documents/credentials.json` с содержимым
   `{"password": "1234qwe", "pincode": 1234}`.

У этого файла есть ещё два отдельных дефекта: он пишется обычным
`Data.write(to:)` без явного `NSFileProtectionComplete` (то есть
получает дефолтный класс защиты `CompleteUntilFirstUserAuthentication`
— читается, пока устройство хоть раз разблокировали после загрузки),
и для него не выставлен `isExcludedFromBackup`, поэтому пароль и пин
уезжают в резервную копию iCloud/iTunes.

Отдельно — экран «Custom Request» держит историю отправленных
запросов (URL, заголовки, тела, ответы сервера) в памяти и рисует её
на экране, при этом в приложении нет затемнения окна при уходе в
фон — снапшот с секретами попадает в `Library/Caches/Snapshots`.

Расположение: `UrlTest/AppDelegate.swift:21-51`,
`UrlTest/CustomRequestViewController.swift:75` и `:371-431`.

### 3. Обработка URL-схем и deeplink

Приложение регистрирует собственную схему `sting://`. Входящий URL
приходит в `SceneDelegate` (`scene:openURLContexts:` и
`connectionOptions` при холодном старте), роутится по host-компоненту
и уходит в `MainViewController` — без какой-либо валидации.

1. **Загрузка произвольного URL в WebView**: `sting://<любой
   host>?url=<target>` доходит до `handleURLContext()`, который
   строит `URLRequest` и вызывает `WKWebView.load()`. Ни allow-list
   хостов, ни ограничения схемы нет — внешнее приложение или
   веб-страница может открыть в контексте UrlTest любую страницу,
   включая фишинговую копию логина.
2. **Открытие произвольного URL наружу**: `sting://redirect?url=<target>`
   попадает в `handleURLForExternalRedirect()` и передаётся в
   `UIApplication.shared.open()`. Это уже не только веб: запускается
   любая схема — `tel:`, `sms:`, схемы сторонних приложений. Host
   `both` дёргает оба пути сразу.
3. **Отказ в обслуживании через deeplink**: если значение параметра
   равно строке `crash`, вызывается `fatalError()` — приложение
   падает по внешнему URL, который может прислать кто угодно.
4. **Разбор URL строковыми операциями**: параметр извлекается не
   через `URLComponents.queryItems`, а как
   `absoluteString.components(separatedBy: "url=")` с взятием
   `parts[1]`. Percent-decoding не выполняется, вложенные `url=`
   ломают разбор — любая будущая фильтрация по такому парсеру
   обходится тривиально.
5. **Источник вызова не проверяется**: `UIOpenURLContext.options`
   (в частности `sourceApplication`) не читается, схема принимает
   вызов от любого приложения на устройстве.
6. **WebView без делегата**: `WKWebView` создаётся конфигурацией по
   умолчанию, `navigationDelegate` не назначен — после загрузки
   чужого URL дальнейшая навигация никак не контролируется.
7. **Universal Links без валидации хоста**:
   `application:continue:restorationHandler:` возвращает `true` для
   любого `webpageURL`, host не сверяется. Опасного sink за этим
   сейчас нет, но обработчик открыт.

Расположение: `Info.plist:10-20` (регистрация схемы),
`UrlTest/SceneDelegate.swift:23-52` (роутинг),
`UrlTest/MainViewController.swift:249-310` (оба flow, метки
`START_POINT` / `CHECK_POINT` / `END_POINT` расставлены автором),
`UrlTest/AppDelegate.swift:55-62`.

### 4. Экран произвольных запросов

Экран «Custom Request» — это по сути встроенный HTTP-клиент:
пользователь задаёт URL, метод, произвольный набор заголовков и тело,
запрос уходит как есть. Единственная проверка ввода — `URL(string:)`
вернул не `nil` и `url.scheme != nil`, то есть схема не ограничена
списком `http`/`https`.

Расположение: `UrlTest/CustomRequestViewController.swift:292-359`.

### 5. Метаданные Info.plist

В `Info.plist` лежат три нестандартных ключа со ссылками:

1. `Internal-URL` = `https://dev.stingray-mobile.ru/login` — внутренний
   dev-эндпоинт, раскрытый в поставляемом артефакте.
2. `URL-Malware` = `https://serak.top/malware`.
3. `URL-RKN` = `wss://1wbetlive.us/rkn`.

Последние два — закладка под проверку репутации доменов: домены с
плохой репутацией и заблокированный в РФ ресурс, зашитые в конфиг.
Все три ключа присутствуют в bundle-plist собранного IPA.

Расположение: `Info.plist:21-26`.

## Что должен найти сканер

Минимально достаточный отчёт — **24** finding'а. Ниже они в том
порядке, в котором их разумно приоритизировать.

**Сеть:**

1. ATS отключён глобально (`NSAllowsArbitraryLoads = true`) —
   небезопасная конфигурация сетевого взаимодействия.
2. Пароль передаётся в HTTP-заголовке `X-Auth-Token`.
3. Push-токен передаётся в HTTP-заголовке.
4. Пароль в query-параметре URL, запрос по cleartext HTTP.
5. Пароль в пути URL.
6. API-ключ (`Authorization: Bearer …`) передаётся по cleartext HTTP.
7. Учётные данные (login/password) в теле запроса по cleartext HTTP.
8. Отсутствует certificate pinning / кастомная валидация цепочки.
9. Ответы на запросы с секретами в URL кэшируются на диск
   (`useProtocolCachePolicy`).

**Хранение:**

10. Захардкоженный токен доступа в коде.
11. Токен сохраняется в UserDefaults вместо Keychain.
12. Учётные данные (пароль, пин-код) записываются в файл открытым
    текстом в `Documents/`.
13. Файл создаётся без `NSFileProtectionComplete`.
14. Файл не исключён из резервных копий (`isExcludedFromBackup`).
15. Нет защиты снапшота приложения при уходе в фон.

**URL-схемы и WebView:**

16. Загрузка произвольного URL из deeplink в `WKWebView`
    (open redirect / arbitrary WebView load).
17. Передача произвольного URL из deeplink в
    `UIApplication.shared.open()` (запуск произвольных схем).
18. Отказ в обслуживании: `fatalError()` достижим по внешнему URL.
19. Разбор URL строковыми операциями вместо `URLComponents`.
20. Источник вызова URL-схемы не проверяется.
21. `WKWebView` без `navigationDelegate` — навигация не ограничена.
22. Universal Links: `webpageURL` принимается без проверки хоста.

**Прочее:**

23. Внутренний dev-эндпоинт раскрыт в `Info.plist`.
24. Ссылки на домены с плохой репутацией / заблокированный ресурс в
    `Info.plist`.

**Что допустимо сворачивать.** Пункты 2–7 — это один класс
(«чувствительные данные в запросе»), сканер может дать их одним
finding'ом со списком contexts, но тогда в contexts обязаны быть все
шесть локаций: два заголовка, query, path, тело. Пункты 13 и 14
допустимо объединить в «файл с секретами без защиты и исключения из
бэкапа». Пункты 16 и 17 сворачивать **нельзя** — это разные классы с
разным fix'ом и разной поверхностью атаки: первый ограничен
веб-контентом внутри приложения, второй позволяет дёргать
произвольные схемы и чужие приложения.

**Спорный пункт.** Экран «Custom Request» принимает URL с любой
схемой (проверяется только `url.scheme != nil`,
`CustomRequestViewController.swift:305`). Обязательным finding'ом это
не считаем — отправка произвольных запросов и есть заявленная функция
экрана, а данные вводит сам пользователь. Но если сканер отмечает
недостаточную валидацию ввода здесь, это не false positive и в
метрику FN такой пункт не идёт ни в одну сторону.

**Что обязательно отдельными finding'ами.** ATS (п.1) — отдельно от
конкретных HTTP-запросов: это конфигурация, а не факт передачи.
Пункт 18 (DoS) — отдельно от пунктов 16/17: тот же вход, но другой
исход и другой fix. Пункт 11 (UserDefaults вместо Keychain) —
отдельно от п.10 (хардкод), это две независимые ошибки: даже
непохардкоженный токен нельзя класть в UserDefaults.

## Где сканер вероятнее всего промахнётся

Два места, из-за которых конкретно на этом приложении набегают
false negative — их стоит проверить отдельно.

**Swift small string optimization.** Строковые литералы длиной до 15
UTF-8 байт включительно компилятор инлайнит в код как immediate, они
**не попадают** в `__cstring` и не видны через `strings`. Проверено
на этом IPA:

- видно: `qweasdzxc123qweasd` (18 б), `password=qwerty123` (18 б),
  `Bearer secret_api_key_12345` (27 б), `credentials.json` (16 б),
  `hasLaunchedBefore` (17 б), push-токен;
- **не видно**: `access_token` (12 б), `password` (8 б),
  `pincode` (7 б), `1234qwe` (7 б).

Сканер, который ищет секреты только по строковой таблице бинаря,
целиком пропустит пункт 12 (пароль `1234qwe` и пин `1234`) и ключ
хранилища из пункта 11. Эти находки достижимы только через анализ
исходников или разбор кода, а не `strings`.

**Taint через строковые операции.** Цепочка пунктов 16/17/19 идёт
`UIOpenURLContext.url` → `absoluteString` → `components(separatedBy:)`
→ `URL(string:)` → `WKWebView.load()` / `UIApplication.open()`. Между
источником и стоком нет ни одного URL-специфичного API, поэтому
анализатор с моделью только по `URLComponents`/`queryItems` связь не
построит. Автор специально уложил оба flow в один метод и разметил их
комментариями `START_POINT` / `CHECK_POINT` / `END_POINT` — это
эталонный тест на taint-трекинг.

## Чего сканер не должен делать

- **Флажить бинарный хардening.** Проверено на артефакте: PIE есть
  (флаг `PIE` в Mach-O header), stack canary есть
  (`___stack_chk_guard` / `___stack_chk_fail`), ARC есть
  (`_objc_release`, `_objc_autoreleaseReturnValue`). Находок здесь
  нет, любое срабатывание — false positive.
- **Флажить `get-task-allow`.** В entitlements подписанного IPA стоит
  `get-task-allow = false` — сборка не debuggable, это корректно.
- **Флажить `cryptid = 0`.** Бинарь не зашифрован, потому что это
  ad-hoc сборка, а не поставка из App Store. Для такого артефакта это
  норма, а не «отсутствие FairPlay-защиты».
- **Флажить debug-настройки из `project.pbxproj`.** `DEBUG=1`,
  `SWIFT_OPTIMIZATION_LEVEL = -Onone`, `ENABLE_TESTABILITY = YES`,
  `GCC_OPTIMIZATION_LEVEL = 0` присутствуют **только в конфигурации
  Debug** (`project.pbxproj:305-330`). В Release их нет. Правило,
  которое читает build settings без разбора конфигурации, даст здесь
  FP.
- **Флажить уязвимые зависимости.** Сторонних SDK и библиотек в
  проекте нет вообще — только системные UIKit/WebKit/Foundation.
- **Флажить `print()` в `AppDelegate.swift:49`** как утечку
  чувствительных данных: там печатается только текст ошибки записи
  файла, без содержимого учётных данных.
- **Флажить отсутствие jailbreak-детекта и anti-debug** как дефект
  этого приложения: оно намеренно спроектировано под подключение
  Frida (о чём говорят названия кнопок «Hook 1+3», «Hook 2» и
  комментарии в `MainViewController.swift:105-124`). Как
  информационный пункт по MASVS-RESILIENCE это допустимо, как
  уязвимость — нет.
