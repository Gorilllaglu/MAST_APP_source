## S-058 — отложенная публикация

### Вопросы

1. **Д-S-058-1.** Почему опубликованное изменение «Названия» и «Описания» не меняет объект? Исправлено ли?
2. **Д-S-058-2.** Какое событие аудита пишется при публикации и отмене и от чьего имени? По ТЗ права проверяются в момент выполнения — чем это подтверждается?
3. **Д-S-058-5.** Почему ручной ввод времени отбрасывается? И почему «Опубликовать» ставит время на час раньше (Д-S-058-3)?
4. **Конфликт.** Что, если отложенное изменение конфликтует с правкой, внесённой позже вручную?
5. **Д-S-058-6.** Почему история показывает ФИО автора администратору вне области?

### СЦ-1. Изменение названия применяется и попадает в аудит (Д-S-058-1, Д-S-058-2)

**Что проверяем:** отложенное изменение применяется целиком, а публикация видна в аудите.

**Шаги.**

1. Под A: «Приложения → Конфигурации» → тестовая конфигурация → изменить «Название» на `ACC-TEST S-058 renamed` и одно значение в редакторе JSON.
2. «Сохранить» → «Сохранить отложенное изменение», комментарий, время — **через календарь** на 5 минут вперёд → «Сохранить».
3. Дождаться статуса «Опубликовано» во вкладке «Отложенные изменения».
4. Перезагрузить страницу, открыть карточку конфигурации.
5. «Отчёты → Аудит» за интервал публикации.

**Ожидаем:**
- название и значение JSON изменены;
- в аудите событие о публикации с указанием изменения и автора.

**Дефект (Medium, Д-S-058-1), если:** статус «Опубликовано», значение JSON применено, а название прежнее.

**Дефект (Medium, Д-S-058-2), если:** события о публикации в аудите нет.

### СЦ-2. Время, введённое вручную (Д-S-058-5)

**Что проверяем:** изменение, запланированное на конкретное время, не публикуется раньше.

**Шаги.**

1. Изменить «Описание» → «Сохранить» → «Сохранить отложенное изменение», комментарий.
2. В поле «Опубликовать не ранее» выделить значение и **набрать с клавиатуры** время на 15 минут позже текущего.
3. Нажать Tab — посмотреть, осталось ли введённое время. Нажать «Сохранить».
4. Посмотреть «Не ранее» в списке отложенных изменений и подождать 3 минуты.

**Ожидаем:** сохранено набранное время, изменение ждёт.

**Дефект (Medium, Д-S-058-5), если:** после Tab время вернулось к исходному, и изменение опубликовано в течение 1–2 минут. Изменение, запланированное на окно обслуживания, уходит сразу.

### СЦ-3. ФИО автора вне области (Д-S-058-6)

**Что проверяем:** администратор вне области не видит ФИО автора отложенного изменения.

**Шаги.** Под B: «Приложения → Конфигурации» → тестовая конфигурация → вкладка «Отложенные изменения» → снять «Показывать только запланированные изменения». Сравнить колонку «ФИО автора» с вкладкой «Владелец».

**Ожидаем:** автор скрыт так же, как владелец («Внешний»).

**Замечание (Low, Д-S-058-6), если:** показано ФИО администратора A при «Внешнем» владельце.

### П-5. SMAPI: отложенные изменения ПУП без нужного права (п. 1 и 3)

**Подготовка.** Тестовое правило Android с известным номером (`appr_id`). Сервисные учётные записи:
- **S1** — разрешены `post api/v3/app-rules/{appr_id}/deferred-changes`, `get` к нему и `post api/v1/app/rule/modify_corporate`;
- **S2** — только `post …/deferred-changes`, без `modify_corporate`;
- **S3** — без методов отложенных изменений.

Токен вводить как в документе ПСИ 23.11 16:00, раздел «Как выполнять команды SMAPI». Срок изменения — через 30 минут:

```bash
T=$(date -u -v+30M +%Y-%m-%dT%H:%M:%SZ); echo $T     # на Linux: date -u -d '+30 min' +%Y-%m-%dT%H:%M:%SZ
```

Запрос создания — один и тот же, меняется только токен:

```bash
curl -s -H "X-Domain-Api-Token: $SMAPI_TOKEN" -H "Content-Type: application/json" -d "{\"comment\":\"ACC-TEST S-058 SMAPI\",\"publish_at\":\"$T\",\"params\":{\"ost_id\":2,\"appr_description\":\"ACC-TEST S-058\"}}" -w '\nHTTP %{http_code}\n' https://<СЕРВЕР>:8085/api/v3/app-rules/НОМЕР_ПРАВИЛА/deferred-changes
```

| Кейс | Токен | Ожидаем | Дефект, если |
| --- | --- | --- | --- |
| К-1. Нет разрешения на метод | S3 | 403 | 201 — Medium. 401 «Invalid token» — замечание Д-S-069-2 |
| К-2. Нет права на прямую правку правила | S2 | 403 | 201 — Medium: через отложенное изменение учётка меняет то, что напрямую ей запрещено. На sb-test 17.0.1 — 201 |
| К-3. Правило вне области учётки | S1, номер правила вне её области | 403 или 404 | 201 — Medium |
| К-4. Блокировка правки при запланированном изменении (п. 3) | S1 | см. ниже | правка прошла |

**К-4.** Пока по правилу есть запланированное изменение (из К-2 или созданное в консоли), выполнить прямую правку правила тем же телом, которое проходит без запланированного изменения: `POST /api/v1/app/rule/modify_corporate`, полный набор полей правила вместе с `appr_silent` (по документации SMAPI). Ожидаем 409 с текстом о конфликте с отложенным изменением. На sb-test 17.0.1 блокировка через SMAPI работала. Важно: 409 с текстом `params and/or conditions must present` — это ошибка тела запроса (Д-S-069-3), а не блокировка.

Если в документации SMAPI есть методы изменения или отмены отложенных изменений — повторить К-1…К-3 и для них.

### П-6. API АРМ: отложенные изменения ПУП без полномочия (п. 1 и 3)

Команды собраны по запросам, которые консоль sb-test 17.0.1 отправляла 23.11:
- создание — `POST /api/v170/deferred-change`;
- правка — `PUT /api/v170/deferred-change/{id}`;
- публикация — `POST /api/v170/deferred-change/publish`;
- удаление — `DELETE /api/v170/deferred-change/{id}`;
- список изменений — `GET /api/v170/deferred-change?entityType=APP_RULE&entityId=…`;
- правило — из списка `GET /api/v1/app-rule?liveSearch=…`, сохранение правила — `PUT /api/v1/app-rule/{id}`.

На ИФТ один раз сверить: под A создать отложенное изменение правила в интерфейсе с открытой Network. Если адреса другие, подставить их в команды.

**Подготовка.**
- **A** — полные права.
- **B** — правила управления приложениями: просмотр и изменение, но **без** полномочия на отложенные изменения ПУП. Область root. На sb-test так был настроен `acc-test-s058` с ролью «Администратор ИТ».
- **Тестовое правило `ACC-TEST S-058 P-6`.** Создать под A: «Приложения → Правила управления → Добавить», любое приложение, назначений нет. Команды меняют только описание, а проверка блокировки сбрасывает разрешения Android правила к умолчанию. Поэтому только тестовое правило.

**Команды.** F12 → Console → вставить один раз под каждым администратором. Если название правила другое, поправить первую строку.

```js
// S-058 П-6: отложенные изменения правила управления приложениями (ПУП) через API АРМ
const RULE = 'ACC-TEST S-058 P-6';   // точное название тестового правила

async function call(method, url, body) {
  const r = await fetch(url, {method, credentials: 'same-origin', body: body === undefined ? undefined : JSON.stringify(body),
    headers: {'Content-Type': 'application/json', 'X-CSRF-TOKEN': document.querySelector('meta[name=_csrf]')?.content || ''}});
  const t = await r.text(); let j = t; try { j = JSON.parse(t); } catch (e) {}
  console.log(method, url, '→ HTTP', r.status, '|', JSON.stringify(j).slice(0, 200));
  return {status: r.status, j};
}

// Правило по названию: номер и текущие поля
async function rule() {
  const r = await (await fetch(`/api/v1/app-rule?start=0&limit=40&liveSearch=${encodeURIComponent(RULE)}`, {credentials: 'same-origin'})).json();
  const x = (r.data || []).find(d => d.title === RULE);
  if (!x) throw new Error('Правило не найдено: ' + RULE);
  return x;
}

// Все отложенные изменения правила и его текущее описание
async function dcList() {
  const x = await rule();
  const L = await (await fetch(`/api/v170/deferred-change?entityType=APP_RULE&entityId=${x.id}&start=0&limit=20&onlyPlanned=false`, {credentials: 'same-origin'})).json();
  for (const d of (L.data ?? [])) console.log(`изменение ${d.id}: ${d.status} | не ранее ${new Date(d.notBefore).toLocaleString('ru-RU')} | ${d.comment} | ошибка ${d.applyError}`);
  console.log(`правило ${x.id}, описание сейчас: ${x.description}`);
}

// Создать отложенное изменение описания правила; срок — через minutes минут. Возвращает номер изменения
async function dcCreate(comment, minutes = 60) {
  const x = await rule();
  const {ae_ot_id, ae_ot_name, type_list, ...settings} = x;
  settings.platform = {platformId: x.platform.platformId, platformName: x.platform.platformName};
  settings.description = comment;
  const r = await call('POST', '/api/v170/deferred-change', {entityId: x.id, entityType: 'APP_RULE', comment,
    notBefore: Date.now() + minutes * 60000, change: {settings}, status: 'PLANNED'});
  return r.j?.data?.id;
}

// Изменить отложенное изменение id: новый комментарий и описание
async function dcEdit(id, comment) {
  const g = await (await fetch(`/api/v170/deferred-change/${id}`, {credentials: 'same-origin'})).json();
  const d = g.data ?? g;
  d.comment = comment;
  if (d.change?.settings) d.change.settings.description = comment;
  return call('PUT', `/api/v170/deferred-change/${id}`, d);
}

// Опубликовать отложенное изменение id сейчас
async function dcPublish(id) {
  const x = await rule();
  return call('POST', '/api/v170/deferred-change/publish', {entityType: 'APP_RULE', entityId: x.id, id});
}

// Удалить отложенное изменение id
async function dcDelete(id) {
  return call('DELETE', `/api/v170/deferred-change/${id}`);
}

// Обычное сохранение правила с новым описанием (проверка блокировки). Только на тестовом правиле
async function ruleSave(description) {
  const x = await rule();
  return call('PUT', `/api/v1/app-rule/${x.id}`, {...x, description,
    platform: {platformId: x.platform.platformId, platformName: x.platform.platformName},
    permission: {default: 'user', permissions: {}}});
}

console.log('Команды П-6 загружены, правило:', RULE);
```

Номер изменения печатает `dcCreate`, все номера видны в `await dcList()`. Срок изменений, которые создают команды, — через 60 минут, чтобы они не опубликовались во время проверки.

**Порядок.**

1. **Под A, контроль.**
   - `a1 = await dcCreate('ACC-TEST P-6 A-1')`, затем `a2 = await dcCreate('ACC-TEST P-6 A-2')`. Ожидаем 201, записать оба номера.
   - `await dcList()` — оба в статусе `PLANNED`.
2. **Под B** — номера `a1`, `a2` подставить числами. После каждой строки выполнить `await dcList()`.

| Кейс | Команда под B | Ожидаем | Дефект (Medium, Д-S-058-7), если |
| --- | --- | --- | --- |
| К-1. Создание | `b1 = await dcCreate('ACC-TEST P-6 B-1')` | 403 | 201 — B создаёт отложенные изменения без полномочия. На sb-test — 201 |
| К-2. Правка чужого | `await dcEdit(a1, 'ACC-TEST P-6 edited by B')` | 403 | 200, комментарий у `a1` сменился. На sb-test — 200, автором стал B |
| К-3. Публикация чужого | `await dcPublish(a1)` | 403 | 200, у `a1` «не ранее» сменилось на текущее время (на sb-test — на час раньше, Д-S-058-3) |
| К-4. Удаление чужого | `await dcDelete(a2)` | 403 | 200, `a2` пропало из `dcList` — чужое запланированное изменение стёрто из истории |
| К-5. Удаление своего | `await dcDelete(b1)` — только если К-1 создал `b1` | 403 | 200 |

Через минуту после К-3 под A выполнить `await dcList()` и записать, что стало с `a1`. На sb-test изменения, которые B правил или публиковал, получали `CANCELLED` «Отказано в доступе». Права проверяются по последнему автору при выполнении, поэтому применить изменение без прав нельзя. Но сорвать, ускорить и стереть чужое изменение можно.

3. **Блокировка правки (п. 3 Сбера), под A.** Пока у правила есть изменение в статусе `PLANNED`: `a3 = await dcCreate('ACC-TEST P-6 A-3')`, затем `await ruleSave('ACC-TEST P-6 LOCK')` и `await dcList()`.
   - **Ожидаем:** 409 или 400, описание не изменилось.
   - **Дефект (Medium), если:** описание стало `ACC-TEST P-6 LOCK` — блокировка есть только в интерфейсе.
   - **Замечание (Low):** 200 с `success:false` и описание прежнее. Так было на sb-test: блокировка работает, но код ответа неверный.

**После проверки** под A удалить оставшиеся изменения (`await dcDelete(<номер>)`) и правило `ACC-TEST S-058 P-6`.

**Если адреса на ИФТ другие.** Под A выполнить действие в интерфейсе → в Network правой кнопкой по запросу → Copy → Copy as fetch. Под B вставить в Console, заменив значение `"x-csrf-token"` вместе с кавычками на `document.querySelector('meta[name=_csrf]').content`.

**Запросы консоли 17.0.1 (сверить на проме по Network):** копирование конфигурации — `POST /api/v170/app-config/copy` `{"id":N}`; конфигурация — `GET /api/v160/app-config/{id}`, сохранение — `PUT /api/v160/app-config/{id}`; отложенные изменения сущности — `GET /api/v170/deferred-change?entityType=APP_CFG&entityId={id}&start=0&limit=20` (без `onlyPlanned=false` отдаёт только запланированные); одно изменение — `GET /api/v170/deferred-change/{dc_id}` (статус, `notBefore`, `publishedAt`, `applyError`, что меняется — `change.settings`, `mainParamsDiff`); журнал аудита — `/api/v83/audit` (запрос не через XHR, проще смотреть в интерфейсе).

Как запускать команды: F12 → Console → вставить целиком → Enter. Команды печатают только статусы, время и названия полей, без содержимого конфигурации.

### Помощник (вставить один раз)


## Дефекты с sb-test 17.0.1 — полное описание

### Д-S-058-1. Отложенное изменение «Названия» и «Описания» получает статус «Опубликовано», но не применяется

**Серьёзность.** Medium — изменение частично теряется при статусе успешной публикации: история изменений и интерфейс расходятся с фактическим состоянием объекта. Подтверждено на полях «Название» и «Описание»; значение конфигурации (JSON) применяется, поэтому прямого разрыва в политике на устройствах не найдено. Остальные поля карточки (подпись настроек, срок подписи) отложенно не проверялись — если они теряются так же, серьёзность выше. Обхода прав и раскрытия данных нет.
**Тип.** функциональный дефект; расхождение с документацией (релизные заметки 17.0, п. 1) и с ТЗ 1.2
**Описание.** Отложенное изменение конфигурации приложения публикуется по расписанию или по кнопке «Опубликовать», получает статус «Опубликовано» и время публикации. Изменённое в нём значение JSON применяется, а изменения «Названия» и «Описания» — нет: ни в карточке, ни в «Текущем значении» окна просмотра изменения.
**Условия.** Консоль 17.0.1, стенд sb-test, fulladmin; тестовая конфигурация «ACC-TEST S-065 A» (Android, `com.android.chrome`, без назначений).
**Шаги воспроизведения.**
1. «Приложения → Конфигурации», выбрать тестовую конфигурацию, изменить «Название» (или «Описание», или значение в редакторе JSON).
2. «Сохранить» → «Сохранить отложенное изменение», заполнить комментарий, время задать через календарь на 3–5 минут вперёд → «Сохранить».
3. Дождаться статуса «Опубликовано» во вкладке «Отложенные изменения».
4. Перезагрузить страницу, открыть карточку и окно просмотра изменения (двойной клик по строке).
**Ожидаемый результат.** Значение объекта равно значению «После публикации».
**Фактический результат.** Статус «Опубликовано», время публикации совпадает с заданным, «Название»/«Описание» прежние; в окне просмотра «Текущее значение» прежнее. Воспроизведено на трёх изменениях (два — «Описание», одно — «Название», в том числе через «Опубликовать»). Для сравнения: отложенное изменение `DownloadRestrictions` 3 → 1 в JSON той же конфигурации применилось; немедленное сохранение «Описания» на соседнем объекте работает.
**Доказательства.** Вкладка «Отложенные изменения» и окно «Просмотр изменения» 2026-10-29 19:22–19:40; запросы `GET /api/v170/deferred-change?entityType=APP_CFG&entityId=27…`, `GET /api/v170/deferred-change/1`, `GET /api/v160/app-config/27`. Скриншоты снять при повторе.
**Влияние.** История изменений утверждает то, чего нет; администратор, ориентирующийся по названию объекта (например, переименование при выводе из эксплуатации), введён в заблуждение. Для заказчика — функция по договору работает не полностью.
**Рекомендация.** Применять все поля опубликованного изменения или не включать в отложенное изменение поля, которые не применяются; при частичном применении ставить статус «Ошибка» и писать событие в аудит; проверить остальные поля карточки и профили/правила управления приложениями.

### Д-S-058-2. Публикация отложенного изменения не отражается в аудите

**Серьёзность.** Medium — ТЗ требует проверки прав в момент выполнения; без события о публикации нельзя ни доказать, что проверка была, ни расследовать, кто и что применил.
**Тип.** расхождение с ТЗ 1.2 (полнота следа) / функциональный дефект
**Описание.** В журнале есть «Создание отложенного изменения назначаемой сущности», но нет события о публикации — ни плановой, ни по кнопке «Опубликовать».

**Шаги воспроизведения.**
1. Создать отложенное изменение с публикацией через несколько минут.
2. Дождаться статуса «Опубликовано».
3. Открыть «Отчёты → Аудит» за этот интервал.
**Ожидаемый результат.** Событие о публикации с указанием изменения, сущности, инициатора (планировщик или администратор) и результата.
**Фактический результат.** В окнах вокруг публикаций (19:22, 19:31) событий о публикации нет.
**Доказательства.** Журнал аудита 2026-10-29, страницы 1–2 при 100 записях; колонки «Действие», «Тип операции», «Время», «Результат».
**Влияние.** Нельзя восстановить, когда и с чьими правами изменение вступило (или должно было вступить) в силу.
**Рекомендация.** Писать в аудит публикацию и её результат, с ссылкой на отложенное изменение и автора.

**Дополнение (2026-10-30).** Так же не аудируется автоматическая отмена при выполнении: в S-058 П-2 изменение после отзыва прав автора получило статус «Cancelled» с причиной «Access denied», но в журнале аудита за 13:32 записей нет. ТЗ требует при отказе записи в аудите. Действия планировщика (публикация и отмена) в журнал не попадают вообще.

### Д-S-058-3. «Опубликовать» записывает «Не ранее» со сдвигом на час назад

**Серьёзность.** Low — на публикацию не влияет (время в прошлом), но время в карточке изменения неверное, что путает разбор и, вероятно, указывает на ошибку часового пояса в этой ветке кода.
**Тип.** функциональный дефект
**Описание.** После «Опубликовать» в 19:34 поле «Не ранее» стало 18:34; «Изменено» — 19:34. Плановые изменения публикуются в заданное время без сдвига.
**Условия.** Консоль 17.0.1, fulladmin, браузер в часовом поясе МСК (запрос выгрузки идёт с `timezoneOffset=-180`).
**Шаги воспроизведения.**
1. Создать отложенное изменение на время в будущем.
2. Во вкладке «Отложенные изменения» выбрать его → «Опубликовать» → «Опубликовать».
**Ожидаемый результат.** «Не ранее» равно текущему времени.
**Фактический результат.** «Не ранее» на час раньше текущего времени.
**Доказательства.** Строка «ACC S-058 P-4 publish now»: «Не ранее» 29.10.2026 18:34, «Изменено» 29.10.2026 19:34, «Опубликовано» 29.10.2026 19:35.

**Рекомендация.** Выставлять время публикации с учётом часового пояса так же, как при обычном сохранении.

### Д-S-058-4. Неверный тип операции в журнале аудита

**Серьёзность.** Low — на работу функций не влияет, но фильтр и корреляция событий по типу операции (в том числе в SIEM) дают неверный результат.
**Тип.** функциональный дефект (аудит)
**Описание.** Операции просмотра записаны как «Запись», операция сохранения — как «Чтение».
**Условия.** Консоль 17.0.1, fulladmin, «Отчёты → Аудит».
**Шаги воспроизведения.**

2. Найти события в «Отчёты → Аудит».
**Ожидаемый результат.** Просмотр — «Чтение», сохранение — «Запись».
**Фактический результат.** «Список отложенных изменений сущности», «Список условий применения», «Чтение записи сущности назначения», «Данные отложенного изменения назначаемой сущности» — «Запись»; «Изменение существующей КП с увеличением версии сущности назначения и версии значения» — «Чтение».
**Доказательства.** Журнал аудита 2026-10-29 19:18–19:32.
**Влияние.** Изменения конфигурации теряются при отборе по типу «Запись»; шум в отборе по записи.
**Рекомендация.** Исправить классификацию операций в аудите; учесть при подготовке «Единого аудита» (ТЗ 3.2).

### Д-S-058-5. Время, введённое с клавиатуры в «Опубликовать не ранее», отбрасывается

**Серьёзность.** Medium — изменение, которое администратор планировал на окно обслуживания, уходит в публикацию немедленно; интерфейс при этом до потери фокуса показывает введённое время.
**Тип.** функциональный дефект
**Описание.** Поле принимает ввод в формате подсказки `DD.MM.YYYY, HH:mm`, но при потере фокуса возвращает значение по умолчанию (момент открытия диалога). Если нажать «Сохранить», не уводя фокус, сохраняется значение по умолчанию. Через календарь время задаётся правильно.
**Условия.** Консоль 17.0.1, fulladmin, диалог «Как сохранить изменения?».
**Шаги воспроизведения.**
1. Изменить объект → «Сохранить» → «Сохранить отложенное изменение», заполнить комментарий.
2. В «Опубликовать не ранее» выделить значение и набрать время на 5 минут позже, например `29.10.2026, 19:31`.
3. Нажать Tab — значение возвращается к исходному. Либо сразу нажать «Сохранить».
**Ожидаемый результат.** Сохраняется набранное время.
**Фактический результат.** Сохраняется время открытия диалога; изменение публикуется в течение 1–2 минут («ACC S-058 P-1 deferred»: набрано 19:25, сохранено «Не ранее» 19:20, опубликовано 19:22).
**Доказательства.** Вкладка «Отложенные изменения», 2026-10-29.
**Влияние.** Непреднамеренная немедленная публикация изменения политики.
**Рекомендация.** Разбирать ручной ввод по маске поля или запретить его; показывать ошибку вместо тихого отката.

Тестовые объекты: отложенные изменения создавались на конфигурации «ACC-TEST S-065 A» (см. S-065).

### Д-S-058-6. История отложенных изменений раскрывает ФИО администратора вне области управления

**Серьёзность.** Low — раскрытие персональных данных администратора (CWE-359); значимо по принципу контраста: в той же карточке владелец вне области скрыт как «Внешний».
**Тип.** функциональный дефект (разграничение доступа к данным)
**Описание.** Администратор с ограниченной областью открывает вкладку «Отложенные изменения» конфигурации, созданной и изменённой администратором вышестоящего уровня. В колонке «ФИО автора» видно ФИО этого администратора. При этом на вкладке «Владелец» той же конфигурации владелец показан как «Внешний», а в списке администраторов ограниченного администратора автор отсутствует. Консоль скрывает личность администратора вне области в одном месте и раскрывает её в другом.
**Условия.** Консоль 17.0.1, стенд sb-test. Автор — fulladmin (корень области root); наблюдатель — rc-itadmin (роль «Администратор ИТ», корень области newemp). Конфигурация «ACC-TEST S-065 A», четыре опубликованных отложенных изменения от 2026-10-29.
**Шаги воспроизведения.**
1. Под администратором с корневой областью создать и опубликовать отложенное изменение конфигурации приложения.
2. Под администратором с ограниченной областью: «Приложения → Конфигурации» → эта конфигурация → вкладка «Отложенные изменения» → снять «Показывать только запланированные изменения».
3. Сравнить колонку «ФИО автора» с вкладкой «Владелец» и со списком «Объекты учёта → Администраторы».
**Ожидаемый результат.** Автор вне области скрыт так же, как владелец («Внешний»).
**Фактический результат.** В «ФИО автора» показано ФИО fulladmin (два слова); на вкладке «Владелец» — «Внешний»; в списке администраторов rc-itadmin только три администратора newemp.
**Доказательства.** `GET /api/v170/deferred-change?entityType=APP_CFG&entityId=27&onlyPlanned=false` → 200 под rc-itadmin. Совпадение установлено сравнением SHA-256 значения из колонки под rc-itadmin и поля «ФИО» fulladmin в списке администраторов под fulladmin (первые 12 знаков `8e385e42da2b`), 2026-10-30. Само значение в документах не приводится.
**Влияние.** Ограниченный администратор узнаёт ФИО администраторов вышестоящего уровня, которых модель доступа от него скрывает. Это материал для социальной инженерии и адресного фишинга против привилегированных администраторов.
**Рекомендация.** Маскировать автора вне области управления так же, как владельца («Внешний»), в ответе `deferred-change`, а не только в интерфейсе; проверить остальные места, где выводится автор или исполнитель (журнал аудита, история изменений).

### Д-S-058-7. API отложенных изменений не проверяет полномочия на отложенные изменения правил управления приложениями

**Серьёзность.** Medium — обход разграничения доступа к функциям управления (CWE-285, CWE-862): администратор без полномочий срывает и удаляет чужие запланированные изменения и стирает их из истории. Применить изменение без прав нельзя — права проверяются при выполнении, поэтому повышения привилегий нет.
**Тип.** дефект безопасности (контроль доступа).
**Описание.** В роли администратора полномочия «Создание», «Изменение», «Удаление» и «Публикация отложенных изменений правил управления приложениями» выключены. Интерфейс кнопки не показывает, но сервер принимает прямые запросы к `/api/v170/deferred-change` от такого администратора. После правки автором изменения становится он сам, поэтому при выполнении изменение отменяется с ошибкой «Отказано в доступе». Публикация и удаление из истории в аудит не попадают (Д-S-058-2), так что следов вмешательства почти не остаётся.
**Условия.** sb-test 17.0.1, 2026-11-23. Администратор `acc-test-s058`: роль «Администратор ИТ» (правила ПУП — просмотр, изменение, удаление; полномочий на отложенные изменения ПУП нет), область root. Тестовое правило `ACC-TEST S-069` (id 173), отложенное изменение 5 создано fulladmin.
**Шаги воспроизведения.**
1. Под fulladmin создать отложенное изменение правила и в Network снять запросы создания, правки и публикации.
2. Войти под администратором без полномочий на отложенные изменения ПУП.
3. В консоли браузера повторить запросы с CSRF-токеном текущей страницы: `PUT /api/v170/deferred-change/{id}`, `POST /api/v170/deferred-change/publish` `{"entityType":"APP_RULE","entityId":173,"id":…}`, `POST /api/v170/deferred-change`, `DELETE /api/v170/deferred-change/{id}`.
**Ожидаемый результат.** 403 на каждый запрос.
**Фактический результат.** PUT — 200, автором изменения стал проверяемый администратор; publish — 200, «Не ранее» сдвинуто на час назад (Д-S-058-3); POST — 201; DELETE своего — 200; DELETE чужого изменения (автор root) — 200, запись удалена из истории. Изменения 5 и 8 при выполнении получили CANCELLED «Отказано в доступе».
**Доказательства.** Ответы сервера в консоли браузера (2026-11-23 11:33–11:36 MSK), статусы изменений через `GET /api/v170/deferred-change?entityType=APP_RULE&entityId=173`.
**Влияние.** Администратор с правом только смотреть и править правила может отменить любое запланированное изменение правила другого администратора (правкой или удалением), опубликовать его раньше времени и удалить записи из истории отложенных изменений. Изменение, запланированное на окно обслуживания, может быть сорвано без следа в аудите.
**Рекомендация.** Проверять полномочия на создание, изменение, удаление и публикацию отложенных изменений на сервере, для каждого типа сущности (ПУП, профиль, конфигурация). Не менять автора при правке чужого изменения либо запрещать правку чужих изменений без отдельного полномочия. Не удалять опубликованные, отменённые и ошибочные изменения из истории. Писать в аудит каждое действие с отложенным изменением.
