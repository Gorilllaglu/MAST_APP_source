# Дефекты ПСИ — согласованный перечень

Составлено 27.11.2026 по итогам проверок на ИФТ и sb-test. Повторяющиеся дефекты описаны один раз, с указанием, где встречались.

---

### 1. S-026 · Чтение политик профиля закрытого типа — `GET /api/v1/profile/{id}/policies`

**Описание.** В роли администратора у типа профиля сняты все действия, включая просмотр. Профили этого типа всё равно видны в его списке. Карточка открывается, а прямой запрос возвращает политики с фактическими значениями. Ограничение по типу сервер проверяет только при создании (там 403), при чтении не проверяет.

**Влияние на безопасность.** Ограничение по типам профилей не защищает данные профилей. Для типов с секретами (Wi-Fi, VPN, Exchange, сертификаты) пароли и ключи получает администратор, которому этот тип закрыт.

**Шаги эксплуатации.**
1. Роль R: только «Профили», в «Profile Permissions» у типа X сняты все действия. Администратор B, у которого R — единственная роль.
2. Под полным администратором создать профиль типа X с тестовым паролем и узнать его номер в Network.
3. Под B: «Профили» → открыть профиль, или F12 → Console → `fetch('/api/v1/profile/<номер>/policies')`. Ответ 200 с политиками и паролем.

**Ожидаемый результат.** Профилей закрытого типа нет в списке. Карточка и `policies` отвечают 403.

### 2. S-029 · Права на загрузку проверяются после разбора файла — `/api/v81/application/upload`, `/api/v130/file-upload`, `/api/v110/letter/attachment/upload`

**Описание.** Администратор без права загрузки отправляет файл прямым запросом и получает 200. Файл попадает во временное хранилище и уходит в appinspector на ФЛК. Права проверяются только на втором шаге, при сохранении.
- **Дистрибутив, проверено на APK.** Загрузка — 200. ФЛК завершается `READY` с разобранными данными пакета: `a01_release_v2v3.apk`, пакет `ru.safemobile.flcdemo` 1.0. Сохранение отвечает 200 `{"asyncTaskState":"FINISHED_ERROR","message":"ACCESS_DENIED","success":false}`, объект не создаётся.
- **Файл для команды.** Ответ 200 с `file_checksum`.
- **Вложение письма.** Без прав — 403. Но если в роли есть права на шаблоны писем, кроме создания, — 200.

На части других ручек права проверяются до приёма файла.

**Влияние на безопасность.** Без права загрузки можно:
- передавать произвольные файлы парсеру appinspector, то есть атаковать поверхность разбора (zip slip, бомбы распаковки, разбор XML);
- исследовать поведение и вердикты ФЛК и подбирать файлы для обхода;
- заполнять временное хранилище;
- нагружать appinspector.

Кроме того, отказ при сохранении приходит с кодом 200 и `success:false`, а не 403.

**Шаги эксплуатации.**
1. Администратор B: на приложения, файлы и шаблоны писем только просмотр.
2. Под B: F12 → Console → скрипт из `api_upload_check.txt`, тест А, строки 1, 5, 6. Ответ 200.
3. Для APK: вердикт ФЛК `READY`, затем `POST /api/v1/application` — 200 с `ACCESS_DENIED`.

**Ожидаемый результат.** 403 на запрос загрузки до того, как файл сохранён и передан в appinspector. На сохранении — 403, а не 200 с `success:false`.

### 3. S-029 · 500 вместо 403 без прав — `/api/v1/cert/upload`, `/api/v120/files/upload`

**Описание.** Без права загрузки ручки отвечают ошибками вместо отказа:
- `/api/v1/cert/upload` (клиентский сертификат) — 500;
- `/api/v120/files/upload` (обои) — 500 или 400, после запроса сессию разлогинило. Причину разлогина нужно перепроверить.

**Влияние на безопасность.** Ответ 500 не позволяет понять, проверены ли права. Это признак того, что обработка файла началась до проверки прав и упала исключением. Неясно, попадает ли файл во временное хранилище и в разбор. Разлогин после запроса — признак необработанной ошибки в обработке сессии.

**Шаги эксплуатации.**
1. Администратор без права загрузки.
2. Скрипт из `api_upload_check.txt`, тест А: строки `certUpload('client')` и `wallUpload()`.
3. Ответ 500 или 400. После `files/upload` сессия завершена.

**Ожидаемый результат.** 403 до обработки файла, сессия сохраняется.

### 4. S-058, S-065 · Отложенные изменения ПУП без полномочия — `/api/v170/deferred-change`

**Описание.** Администратор с правом просмотра и изменения правил управления приложениями, но без полномочия на отложенные изменения ПУП, может через API:
- создать отложенное изменение;
- изменить чужое — автором становится он;
- опубликовать чужое досрочно;
- удалить своё и чужое, удалённое пропадает из истории.

Интерфейс эти действия скрывает, сервер их не проверяет. При выполнении права проверяются по последнему автору, поэтому изменение такого администратора получает `CANCELLED` «Отказано в доступе».

**Влияние на безопасность.** Без полномочия можно сорвать запланированные изменения других администраторов (правка делает его автором, и изменение отменяется), ускорить их или удалить вместе с историей. Нарушены целостность процесса изменений и прослеживаемость.

**Шаги эксплуатации.**
1. Под полным администратором создать два отложенных изменения тестового правила.
2. Под B: F12 → Console → команды П-6 из документа S-058 (`dcCreate`, `dcEdit`, `dcPublish`, `dcDelete`). Все отвечают 200 или 201.
3. В истории правила изменения B есть, удалённое чужое изменение пропало.

**Ожидаемый результат.** 403 на создание, правку, публикацию и удаление для администратора без полномочия.

### 5. Миграция ролей при обновлении на 18 — права на всю ветку конфигураций приложений

**Где встречалось:**
- S-058 и S-065 — права на конфигурации приложений и отложенные изменения;
- S-099 — выдача новых полномочий при обновлении («баг при миграции ролей на 18», отметка 20.11).

**Описание.** У существующих учётных записей после обновления права действуют на всю ветку «Конфигурации приложений», а не только на отмеченные в роли пункты. На новой учётной записи с той же ролью не воспроизводится.

**Влияние на безопасность.** После обновления администраторы без собственных действий получают права, которых у них не было. Это неявное повышение привилегий. Ролевая модель с минимальными правами не работает, пока роли не проверят вручную.

**Шаги эксплуатации.**
1. До обновления: роль с частичными правами в ветке конфигураций приложений, например только просмотр.
2. После обновления на 18 под администратором с этой ролью выполнить действие вне его прав: изменить или удалить конфигурацию, создать отложенное изменение. Действие проходит.
3. Создать новую учётную запись с той же ролью и повторить. Действие отклонено.

**Ожидаемый результат.** Миграция сохраняет точный набор прав. Новые полномочия выдаются только по заявленному правилу и видны в роли.

### 6. S-065 · Удаление конфигурации приложения без проверки области управления — `DELETE /api/v1/application/{id}`

**Описание.** Администратор с правом удаления удаляет прямым запросом конфигурацию вне своей области (для него она «Внешняя»). Копирование чужой конфигурации (`app-config/copy`) сервер при этом отклоняет с 403. Удаление — нет.

**Влияние на безопасность.** Администратор одного подразделения удаляет конфигурации других подразделений, и приложения на их устройствах теряют настройки: почту, VPN, ограничения. Нарушены целостность и доступность, разграничение по областям не действует. Номера объектов идут подряд, поэтому их можно перебрать.

**Шаги эксплуатации.**
1. Под полным администратором создать тестовую конфигурацию в корне, вне области B.
2. Под B (ограниченная область, есть право удаления): F12 → Console → `fetch('/api/v1/application/<номер>', {method: 'DELETE', headers: {'X-CSRF-TOKEN': document.querySelector('meta[name=_csrf]').content}})`.
3. Ответ 200, конфигурация пропала из списка у полного администратора.

**Ожидаемый результат.** 403 или 404, конфигурация на месте.

### 7. S-093, S-094 · Отправка кода приглашения сотруднику вне области управления — `POST /api/v110/bootstrap/codes/qrsendemail`

**Описание.** Администратор с правами на коды отправляет на почту код сотрудника вне своей области. Без прав на коды все операции отклоняются с 403.

**Влияние на безопасность.** Операция над чужими объектами вне области управления. Вместе с правкой e-mail сотрудника без проверки области (дефект S-026, `PUT /api/v1/employee`, если подтвердится) код уходит на подставленный адрес. Тогда можно зарегистрировать устройство от имени чужого сотрудника.

**Шаги эксплуатации.**
1. Администратор B: права на коды, область — подразделение 1.
2. Под полным администратором выпустить код сотруднику подразделения 2 и записать `code_id`.
3. Под B: `POST /api/v110/bootstrap/codes/qrsendemail?code_id=<номер>` с CSRF-токеном. Ответ 200, письмо отправлено.

**Ожидаемый результат.** 403, письмо не отправлено.

### 8. S-093, S-094 · Пустой белый список групп и право «свой код» дают доступ к кодам всех сотрудников

**Описание.**
- **Все права на коды, пустой белый список, нет права на свой код.** Просмотр, создание и отправка кодов любых сотрудников — 200, деактивация — 403.
- **То же, но с правом на свой код.** Все операции — 200, в том числе с кодами других учётных записей.

**Влияние на безопасность.** Ограничение по группам — суть S-093 — не работает: пустой список означает «все», а не «никто». Право на свой код распространяется на чужие. Администратор видит цифры кода другого сотрудника или администратора и может зарегистрировать устройство от его имени. Деактивация закрыта, а остальные операции нет: проверки идут по каждой операции отдельно и не согласованы.

**Шаги эксплуатации.**
1. Два администратора с полными правами на коды и пустым белым списком: A1 с правом на свой код, A2 без него. Каждый связан со своей записью сотрудника.
2. Под полным администратором выпустить коды обоим.
3. Под A1 и A2 по очереди: список кодов, просмотр, создание и отправка по чужой записи (кейс 3 документа 19.11 12:30). Ответы 200.

**Ожидаемый результат.**
- Пустой белый список — нет доступа к кодам сотрудников. Исключение — свой код при наличии этого права.
- Право на свой код действует только на собственный код.
- Все операции подчиняются одним и тем же ограничениям.

### 9. S-093, S-094 · Повторная деактивация и отправка деактивированного кода отвечают 200 — замечание

**Описание.** Деактивация уже деактивированного кода отвечает 200. Отправка деактивированного кода на почту тоже 200. На 17.0.1 вместо этого было 500.

**Влияние на безопасность.** Сервер не проверяет состояние кода. Сотрудник получает письмо с неработающим кодом, а такие письма похожи на фишинг. Ответы не отражают фактическое состояние, это мешает мониторингу и разбору событий.

**Шаги эксплуатации.**
1. Деактивировать код: `POST /api/v110/bootstrap/codes/deactivate?code_id=<номер>`.
2. Повторить деактивацию. Ответ 200.
3. Отправить код: `qrsendemail?code_id=<номер>`. Ответ 200.

**Ожидаемый результат.** 400 или 409 с причиной «код деактивирован». Письмо не отправляется.

### 10. ФЛК-1 · S-100, п. 4.5 договора · IPA: корректность подписи кода не проверяется

**Описание.** АРМ принимает два изменённых пакета:
- **y01** — после подписи в Info.plist изменён идентификатор пакета;
- **y02** — в исполняемом файле затёрты последние 64 байта, это блок подписи кода.

Похоже, проверяется только наличие подписи (неподписанный `s5-unsigned` вендора отклоняется), а хеши кода и запечатанных ресурсов (`_CodeSignature/CodeResources`) не сверяются.

**Влияние на безопасность.** В каталог попадает дистрибутив, изменённый после подписи. АРМ показывает идентификатор и версию из подделанного Info.plist, и белые списки по идентификатору опираются на подделку. Контроль целостности по п. 4.5 не выполняется. iOS такой пакет, скорее всего, не установит, поэтому для пользователей это ещё и сломанная раздача.

**Шаги эксплуатации.** «Приложения → Добавить» → загрузить `FLK-1_ipa_code_signature/y01…ipa` и `y02…ipa`. Оба приняты.

**Ожидаемый результат.** Отказ: подпись кода некорректна.

### 11. ФЛК-3 · Серверные сертификаты, п. 4.3 · Нет проверки цепочки до доверенного корня

**Описание.** АРМ принимает:
- **z01** — самоподписанный сертификат (RSA 1024, SHA-1);
- **e03 вендора** — цепочка без корня.

Хранилища доверенных корней нет. Проверяется только согласованность цепочки внутри файла, любой самоподписанный сертификат принимается.

**Влияние на безопасность.** В систему загружается сертификат, не выпущенный доверенным центром сертификации. Поддельный или подменённый серверный сертификат не отсекается, и доверие к нему ничем не обосновано.

**Шаги эксплуатации.** «Серверные сертификаты» → загрузить `FLK-3_cert_trusted_root/z01…pem` или `05_chain/e03…pem` вендора. Сертификат принят.

**Ожидаемый результат.** Отказ: цепочка не доходит до доверенного корня.

### 12. ФЛК-4 · Серверные сертификаты, п. 4.3 · Глубина цепочки не ограничивается

**Описание.** **z02** — цепочка из 7 сертификатов — загружается. Параметра глубины в настройках нет, ограничение «в соответствии с заданной глубиной» не действует.

**Влияние на безопасность.** Принимаются цепочки произвольной длины через неожиданные промежуточные центры. Растёт поверхность и нагрузка при разборе. Требование договора не выполнено.

**Шаги эксплуатации.** Загрузить `FLK-4_cert_chain_depth/z02…pem`. Сертификат принят.

**Ожидаемый результат.** Отказ, если глубина больше заданной. Глубина задаётся в настройках ФЛК.

### 13. ФЛК-5 · Отправка файла, п. 4.6 · Документы с макросами под именами .docx и .xlsx проходят

**Описание.** **f01** и **f02** — на самом деле docm и xlsm: в `[Content_Types].xml` тип `…macroEnabled.main+xml`, внутри `vbaProject.bin`. Их принимают как docx и xlsx, хотя docm и xlsm нет в белом списке. Перепроверить после донастройки allow-list для `file-upload`.

**Влияние на безопасность.** На устройства доставляется документ с исполняемым кодом (макросом) в разрешённом формате. Цель п. 4.6 — исключить код вне разрешённых форматов — не достигается. Мобильный Office макросы не выполняет, поэтому риск появляется, когда файл переносят на Windows.

**Шаги эксплуатации.** Команда «Отправить файл» → загрузить `FLK-5_office_macros/f01…docx` и `f02…xlsx`. Оба приняты.

**Ожидаемый результат.** Отказ: реальный тип (docm, xlsm) не входит в белый список.

### 14. S-028 · В выгрузке отчёта инвентаризации остаются метаданные шаблона — замечание

**Описание.** Отчёт строится по шаблону XLSX, свойства которого при формировании не сбрасываются. В `docProps/core.xml` и `docProps/app.xml` остаются автор шаблона (ФИО сотрудника вендора), даты создания и изменения, ревизия и приложение из рабочей среды разработчика.

**Влияние на безопасность.** Отчёты расходятся внутри организации и могут уходить третьим лицам, и в каждом есть персональные данные сотрудника вендора и сведения о его рабочей среде. Даты файла не соответствуют моменту выгрузки, это мешает разбору инцидентов.

**Шаги эксплуатации.**
1. «Данные об устройстве» → «Выгрузить», любой вид отчёта.
2. Открыть «Файл → Свойства» или распаковать XLSX и посмотреть `docProps/core.xml`.

**Ожидаемый результат.** Автор — название продукта или пусто, даты — момент формирования отчёта.

### 15. SMAPI · Без разрешения на метод — 401 «Invalid token» вместо 403 — замечание

**Где встречалось:**
- S-069 — `app/rule/modify_corporate`, `app-rules/{id}/deferred-changes`;
- S-070 — `license/info`;
- S-058 П-5 — тот же ответ ожидается в К-1.

**Описание.** Если у сервисной учётной записи нет разрешения на метод или разрешения отозваны, SMAPI отвечает `401 {"error":"Invalid token"}`. Это тот же ответ, что на недействительный токен. В журнале SMAPI вызов записан как «Authorization error», то есть токен сервер принял.

**Влияние на безопасность.** Отказ по правам неотличим от недействительного токена. Мониторинг и разбор инцидентов получают ложную картину: похоже на компрометацию или истечение токена, а не на попытку вызвать запрещённый метод. Интеграции начинают перевыпускать токены вместо того, чтобы исправлять права.

**Шаги эксплуатации.**
1. «Объекты учёта → Service accounts» → снять разрешение на метод.
2. Вызвать этот метод действующим токеном. Ответ 401 «Invalid token».
3. Вызвать разрешённый метод тем же токеном. Ответ 200.

**Ожидаемый результат.** 403 с текстом «метод не разрешён». 401 — только для отсутствующего или недействительного токена.
