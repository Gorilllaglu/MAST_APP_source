# F-RC-4 — Настройка «только просмотр» не действует: секционное право раскрывает всю ветку удалённого экрана

**Severity: High** (самостоятельно — повышение фактических полномочий относительно
настроенных; в связке с [F-RC-9](F-RC-9-covert-screen-capture.md) даёт Critical)

| | |
|---|---|
| Продукт | SafeMobile / SafePhone MDM, консоль Altair 17.0.1 |
| Стенд | `https://sb-test.safe-mobile.ru:8443` (`85.198.96.253`) |
| Дата подтверждения | 21.10.2026 |
| Статус | подтверждено измерением, воспроизводится за минуту |

---

## Суть

Администратор может в интерфейсе консоли выдать роли **только право «просмотр»**
по удалённому экрану, сняв галочки с «управления», «буфера обмена» и
«подключения без подтверждения сотрудника». Интерфейс это позволяет, роль
сохраняется корректно — в базе у неё действительно остаётся только `1007090`.

**Но настройка не действует.** Если в роли присутствует **секционное право
раздела `10000`**, учётка с этой ролью получает **всю ветку** удалённого экрана,
включая `PERM_MOBILE_REMOTE_CONTROL_WITHOUT_CONFIRMATION` — «без подтверждения
сотрудника». Сервер принимает от такой учётки сеансы с повышенными привилегиями,
и агент на устройстве их исполняет.

Штатная роль **«Администратор ИТ» (id 1)** содержит `10000`, поэтому проблема
воспроизводится на поставочной конфигурации, а не на искусственной.

---

## Затронутые полномочия

| id | имя | назначение |
|---|---|---|
| `10000` | секционное право раздела | **триггер**: раскрывает ветку целиком |
| `10070` | `PERM_MOBILE_REMOTE_CONTROL` | родительское |
| `1007090` | `..._VIEWING` | просмотр экрана |
| `1007091` | `..._CONTROL` | управление устройством |
| `1007092` | `..._CLIPBOARD` | общий буфер обмена |
| `1007093` | `..._WITHOUT_CONFIRMATION` | **захват без подтверждения сотрудника** |

---

## Воспроизведение

### Шаг 1. Что записано в роли

```
GET /api/v160/roles/1/privileges
```

В ответе из ветки пульта присутствует **только** `1007090`:

```json
{"rolePrivileges": [ …, {"roleId": 1, "privId": 10000}, …,
                     {"roleId": 1, "privId": 1007090}, … ]}
```

`1007091`, `1007092`, `1007093` и `10070` — отсутствуют.

### Шаг 2. Что реально действует у учётки с этой ролью

Завести учётку с ролью 1 (`POST /api/v80/admin`, `"roles": [1]`), войти под ней и
открыть страницу пульта. Сервер сам вписывает эффективный набор полномочий в
разметку страницы:

```html
<script nonce="…">
  var spProfile = { permissions: [ …,
    "PERM_MOBILE_REMOTE_CONTROL",
    "PERM_MOBILE_REMOTE_CONTROL_CLIPBOARD",
    "PERM_MOBILE_REMOTE_CONTROL_CONTROL",
    "PERM_MOBILE_REMOTE_CONTROL_VIEWING",
    "PERM_MOBILE_REMOTE_CONTROL_WITHOUT_CONFIRMATION" ], … };
</script>
```

В консоли браузера это видно одной строкой:

```js
spProfile.permissions.filter(p => p.includes('REMOTE_CONTROL'))
```

Всего у роли 129 записанных прав — у учётки **267 эффективных**.

### Шаг 3. Триггер в чистом виде

Создать роль с **единственным** правом `10000` и повесить на тестовую учётку.
Результат: 23 эффективных полномочия, среди которых **все пять** по удалённому
экрану, включая `_WITHOUT_CONFIRMATION`.

### Шаг 4. Контрольный опыт (обязателен)

Роль с единственным правом `1007090` и **без** `10000` ведёт себя правильно:
2 эффективных полномочия, только `..._VIEWING`, а попытка поднять сеанс с
`Manage` отбивается сервером — «Недостаточно прав».

Разница между шагом 3 и шагом 4 и есть находка.

### Шаг 5. Это не только интерфейс — сервер принимает

Учётка с ролью 1 публикует оффер с повышенными привилегиями:

| запрошено оператором | сервер | доставлено агенту |
|---|---|---|
| `[]` | принято | `privileges=[]` |
| `["Manage"]` | **принято** | `privileges=[MANAGE]` |
| `["WithoutConfirmation"]` | **принято** | `privileges=[WITHOUT_CONFIRMATION]` |
| `["Manage","Clipboard","WithoutConfirmation"]` | **принято** | `[MANAGE, CLIPBOARD, WITHOUT_CONFIRMATION]` |

Проверено на **настоящем агенте** 17.0.2.1 (журнал устройства):

```
HandleWebRTCSignalUseCaseImpl] WebRTCStart received room=903
    privileges=[MANAGE, CLIPBOARD, WITHOUT_CONFIRMATION]
```

### Готовый инструмент

```bash
python3 cli/permcheck.py --base <host:8443> --role 1 \
    --login <учётка> --password '<пароль>'
python3 cli/permcheck.py --base <host:8443> \
    --login <учётка> --password '<пароль>' --try-session --mcc <СВОЁ устройство>
```

## Влияние

1. **Разрыв между заявленной и фактической конфигурацией.** Администратор,
   ограничивший роль просмотром, уверен, что подчинённые администраторы не могут
   управлять устройствами и не могут смотреть экран скрытно. Фактически могут.
   Это не «неудобство настройки», а молчаливое расхождение: консоль показывает
   одно, система делает другое.
2. **Скрытное наблюдение становится доступно рядовому администратору.** Право
   `_WITHOUT_CONFIRMATION` приводит к захвату экрана сотрудника без его согласия
   — см. [F-RC-9](F-RC-9-covert-screen-capture.md), механизм подтверждён на
   настоящем агенте.
3. **Полный контроль над устройством.** `MANAGE` открывает инжект жестов, то есть
   действия от имени сотрудника; `CLIPBOARD` — доступ к буферу обмена.
4. **Нельзя построить разделение обязанностей.** Любая роль, содержащая
   секционное право раздела, эквивалентна полному доступу к удалённому экрану.

Отягчающее обстоятельство: по [F-RC-7/F-RC-8](F-RC-7-8-audit-gaps.md) факт
трансляции экрана в журнал аудита **не попадает никогда**, поэтому злоупотребление
этим расширением полномочий не оставляет следа.

---

## Рекомендации

1. **Не раскрывать дочерние полномочия из секционного права.** Секционное право
   должно давать доступ к разделу интерфейса, а не ко всем операциям внутри него.
2. **Проверять привилегии сеанса по явно выданным правам**, а не по вычисленному
   «эффективному» набору; как минимум — `_CONTROL`, `_CLIPBOARD` и
   `_WITHOUT_CONFIRMATION` должны требовать явной выдачи.
3. **Показывать администратору фактический набор.** В карточке роли выводить
   предупреждение: «секционное право даёт также …» со списком.
4. Отдельно отметить `_WITHOUT_CONFIRMATION` в интерфейсе как особо чувствительное
   и требовать подтверждения при выдаче.

---

## Что рядом проверено и работает правильно

* Роль **без** `10000` ограничивает полномочия корректно, сервер отбивает
  эскалацию — «Недостаточно прав».
* Область управления соблюдается: устройство вне подразделения учётки даёт
  «Устройство не найдено» (неотличимо от несуществующего).
* Дочерние права в интерфейсе консоли присутствуют и выдаются раздельно.

> **Поправка к ранним черновикам.** В первых записях механизм был описан неверно:
> «родительское 10070 раскрывается во все дочерние, а дочерних прав в консоли нет».
> Это опровергнуто измерением: дочерние права в консоли есть, роль без `10000`
> работает правильно, а раскрывает ветку именно секционное `10000`.
