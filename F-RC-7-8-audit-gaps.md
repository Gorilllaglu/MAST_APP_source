# F-RC-7 / F-RC-8 — Факт трансляции экрана не фиксируется в журнале аудита

**Severity: Medium**

| | |
|---|---|
| Компоненты | консоль Altair 17.0.1 (страница пульта `/remotecontrol`), журнал аудита |
| Дата подтверждения | 21.10.2026 |
| Статус | подтверждено измерением и чтением кода страницы |

---

## Что работает правильно (важно для контекста)

**Старт сеанса аудируется на сервере и аудируется хорошо.** За 12 часов
зафиксировано 37 записей, в каждой — кто, когда, какое устройство и в каком
режиме:

```json
{"login":"fulladmin","procd_name":"SP_REMOTE_CONTROL_ADM_START_SESSION_VIEW",
 "procd_desc":"Открытие сессии удаленного управления в режиме просмотр",
 "person":"admin admin","roles":"Все полномочия","controlRegion":"root",
 "values":"ИД МСК:730","trns_res":"Успех","aud_ts":"2026-10-21T09:39:06.875Z"}
```

Режимы различаются (`_VIEW`, `_CONTROL`, `_CLIPBOARD`, `_WITHOUT_CONFIRMATION`),
учётки различаются, и — что существенно — **сеансы, поднятые через API в обход
браузера, тоже записываются**. Аудит старта от клиента не зависит.

Это стоит сохранить при исправлении приведённого ниже.

---

## F-RC-8 — запись «Начало трансляции экрана» не создаётся никогда

В каталоге аудируемых действий (`GET /api/v1/audit/actions`, 1312 записей) для
фичи предусмотрено отдельное действие:

```json
{"name":"SP_REMOTE_CONTROL_ADM_START_SCREEN_SHARING",
 "desc":"Начало трансляции экрана","write":true}
```

Отправляет её **браузер**, из обработчика состояния ICE
(`WebRTCService.js:614-617`):

```js
case 'connected':
  this.webrtcWasConnected = true;
  const auditSignal = { type: 'audit.startOfScreenBroadcast' };
  this.sendSignal(auditSignal);
```

а адресат формируется так (`WebRTCService.js:534-536`):

```js
case 'audit.startofscreenbroadcast':
  destination = `/webrtc.audit.startOfScreenBroadcast.${this.roomId}`;
  break;
```

**Без префикса `/app`**, в отличие от оффера (`/app/signal.offer.{roomId}`).
Такой адресат не маршрутизируется — брокер на него даже не отвечает.

Замер обеих адресаций:

| адресат | ответ брокера | запись в журнале |
|---|---|---|
| `/webrtc.audit.startOfScreenBroadcast.{room}` — **как в пульте** | **нет вовсе** | нет |
| `/app/webrtc.audit.startOfScreenBroadcast.{room}` | `{"state":true,"data":"ok"}` | **создана** |

Следствие: за 12 часов при 37 зафиксированных стартах сеансов — **ноль записей о
трансляции экрана**.

## F-RC-7 — аудит трансляции в принципе доверен клиенту

Даже если исправить адресацию, запись о самом чувствительном событии —
фактическом начале показа экрана — остаётся **сообщением от браузера**.
Оператор, управляющий своим браузером (девтулзы, прокси, собственный клиент),
может её просто не отправить. Сервер при этом знает всё необходимое: он выдал
комнату, он доставил команду устройству, он получает сигналы сеанса.

---

## Сопутствующие пробелы

| | |
|---|---|
| **Завершение сеанса не аудируется** | `SP_REMOTE_CONTROL_ADM_END_SESSION` — ноль записей при 37 стартах. По журналу невозможно установить длительность наблюдения за экраном |
| **Отказы по правам не аудируются** | отклонённые попытки поднять сеанс с лишними привилегиями следа не оставляют; перебор полномочий не виден |
| **Со стороны устройства записи нет вовсе** | в истории команд устройства (`GET /api/v1/mobile/<mcc>/command`) при полутора десятках сеансов — только запись «Синхронизация настроек» |

## Воспроизведение

```bash
# прочитать журнал за последние часы и отфильтровать действия по пульту
python3 cli/auditlog.py --base <host:8443> --hours 12
```

Инструмент печатает сводку по типам действия и отдельно отмечает отсутствие
`START_SCREEN_SHARING`. Ручка журнала — `POST /api/v83/audit`, сетка
асинхронная: строки приходят событием в STOMP с полями
`aud_id` / `login` / `procd_name` / `values`.

---

## Влияние

Организация видит в журнале, что сеанс **открывали**, и никогда не видит, что
экран **действительно транслировали** и сколько времени. Для продукта класса MDM,
где удалённый просмотр экрана — самая чувствительная к приватности операция, это
означает невозможность расследования и контроля за самими администраторами.

В сочетании с [F-RC-9](F-RC-9-covert-screen-capture.md) (скрытный захват) и
[F-RC-4](F-RC-4-privilege-branch-expansion.md) (полномочие выдаётся неявно)
получается: наблюдение без согласия сотрудника и без следа в журнале.

---

## Рекомендации

1. **Писать аудит трансляции на сервере** — в момент, когда серверу известно о
   начале сеанса, а не по сообщению браузера. Клиентское сообщение можно оставить
   как дополнительный сигнал, но не как единственный источник.
2. Починить адресацию (`/app/…`) — это снимет F-RC-8, но **не снимает F-RC-7**.
3. **Фиксировать завершение сеанса** и длительность.
4. **Фиксировать отказы** по правам — иначе перебор полномочий невидим.
5. Рассмотреть отражение факта наблюдения в журнале **на самом устройстве**,
   доступном сотруднику.
